# 第 15 章：任务队列、投递与恢复

导出报表要跑 40 秒。页面可以先显示“已受理”，稍后轮询状态；前提是服务端已经把任务可靠地交给一个可以在请求结束后继续工作的执行方。把 handler 改成启动 goroutine 就返回，只改变了等待方式，进程重启后任务仍可能消失。

## 任务状态与消息投递各有一份账

以设计中的导出接口为例，提交成功返回 `202 Accepted` 和任务 ID；详情接口只允许任务所属的用户或授权角色读取。任务状态表记录 queued、running、succeeded 或 failed，并保存可查询的结果引用。消息只负责把任务 ID 交给消费者。浏览器关闭或请求断开不自动取消已接收的任务；取消要有自己的接口和状态转换，并处理取消与完成同时发生的情况。

| 确认发生在哪一层 | 能确定什么 | 还要检查什么 |
| --- | --- | --- |
| HTTP 返回任务 ID | 应用确认了自己的接纳条件，例如已提交任务和待发送记录 | worker 是否开始执行 |
| Broker 确认发布 | Broker 按当前队列与发布配置确认了发布；还要处理未路由的消息 | 业务结果是否已经提交 |
| worker 提交结果后 ACK | worker 通知 Broker 这次投递可以确认 | ACK 丢失后，重复投递是否会造成第二次业务写入 |

## 用 Outbox 处理两次写入之间的崩溃

如果先写任务表再发消息，服务可能在两步之间退出，数据库里就会留下没人执行的任务。反过来先发消息，worker 可能读不到任务，或者拿到一条最终没有提交的任务。

Outbox 的办法是用同一个数据库事务写入任务行和一条待发布事件。独立转发者读出待发事件，发布并确认后标记已发送。如果发布成功、标记前退出，重启后可能再发一次。Outbox 把“是否还有东西要发”留在数据库里，重复仍由消费者处理。监控时看最旧待发记录的年龄；只看队列深度，发现不了积压在数据库里的消息。

## 让下一进程只靠数据库恢复

[真实重启实验](../../../labs/part2-backend/chapter12/report-sql/README.md)让任务和本地待办在同一事务提交。worker 写完结果却没确认就退出，新进程扫描未确认待办。它先检查结果是否已经落库，再执行条件写，最后标记确认。验收时比较三个量：结果内容、结果写入次数和待办确认标记。恢复前后的结果一样、写入次数保持 1，确认从 0 变 1。

这里的本地待办表把「是否还要投递」保存下来。迁移到真实 Broker 时，转发者还要处理发布确认，消费者要处理 ACK 丢失和重投递；如果报表写到对象存储，也需要独立校验外部写入的幂等边界。

## 允许重复投递，约束业务副作用

worker 处理完再确认。若提交结果后、ACK 到达前断开，Broker 可以重新投递。消费者用稳定的事件 ID 去重；去重记录和业务修改应在同一个事务里提交，或者由目标存储按任务 ID 做唯一写入。外部系统如果不支持幂等，必须另行定义查证和补偿方法，不能用本地去重表承诺外部副作用只发生一次。

队列可以缓冲短时突发。生产持续比消费快时，队列只会推迟过载的暴露。记录入队速率、处理速率、最旧消息年龄和失败重试次数；短时故障做有界退避，格式错误等永久失败进入失败记录或死信队列，经核对后再重放。对同一任务的乱序更新，按状态或版本做条件写入，避免旧事件把已完成任务改回执行中。

## 踩坑清单

- 先 ACK 再提交业务状态，提交失败时可能没有机会自动重做；只在“这条工作可以安全移出队列”时确认。
- 进程内 channel 可以练接纳与退出，但进程重启后不保留消息；[异步任务实验](../../../labs/part3-agent/chapter31/async-tasks/README.md)可用于观察任务生命周期，不能验证 Broker 的持久投递。
