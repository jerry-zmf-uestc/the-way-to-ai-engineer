# 第 20 章：可观测性与事故诊断

报表页面一直转圈，worker 却每秒都有成功记录。先判断用户在哪个阶段等：提交请求没返回，还是已经拿到任务 ID 但迟迟没有结果？两类故障需要不同的时间起点和分母。

## 从用户影响缩小到任务阶段

给提交定义「多少合法请求在预算内收到接纳」，给后台执行定义「多少已接纳任务在预算内完成」。把接纳数、完成数、拒绝数和等待最久的任务年龄放在同一时间窗口看。吞吐保持不变且最老等待持续增长，说明任务仍在完成，但服务率追不上到达率。若队列深度低而查询变慢，应检查读路径或下游连接等待。

一次导出横跨多个 HTTP 请求和后台执行。请求 ID 用于追踪一次 HTTP 调用，任务 ID 用于关联接纳、入队、执行和查询，重复投递还需要区分尝试。任务 ID 放进日志与追踪属性；指标维度使用路由或结果类别，避免每个任务生成独立指标序列。采样造成的 Trace 缺口不能证明某一步没执行。

## 先记录故障，再确认止损是否有效

打开[积压观察 Lab](../../../labs/part2-backend/chapter21/report-backlog/README.md)或浏览器综合实验，记录两次队列年龄、完成速率和受影响的任务 ID。提出一个可以验证的假设，例如消费者暂停导致任务排队。恢复消费后，检查旧任务是否完成、深度和年龄是否归零、后续查询是否恢复。记录同一任务在故障前后的时间，避免用「重启后看起来好了」替代证据。

以下保留服务发现与发布边界作为排查下游问题时的参考。远程调用主线见[第 17 章](chapter17.md)。

## 服务名、地址和可接流量是三件事

调用方使用稳定的逻辑名，如 `report-worker`。服务发现负责提供路由目标；负载均衡负责选择本次连接或调用落到哪里；就绪检查负责描述实例当前是否适合接收新流量。三者可能由客户端、代理或平台分别承担。以 Kubernetes 的普通 Service 为例，客户端通常访问稳定的 Service 地址，由平台转发到后端；有些注册中心方案则由客户端解析实例列表并选择目标。

用 A、B 两个实例想象一次滚动发布：B 启动且就绪后才加入流量；A 标记不就绪后，等待路由更新并处理在途请求，最后在截止时间内关闭。解析结果、代理和长连接可能还保留 A，摘除不会立即取消旧连接；调用方仍需有超时，实例仍需拒绝已不能接纳的新工作。如何退避与确认结果见[第 18 章](chapter19.md)，进程生命周期见[第 21 章](chapter21.md)。

## 把配置当成一次可追溯的变更

请求时限、队列容量、下游地址都可能改变运行行为。启动配置集中加载和校验；动态配置先验证范围，再以完整快照切换，记录版本和生效范围，保留最后一份可用配置或明确拒绝启动的条件。例如把导出并发从 4 改为 40，即使代码没发版，也会把数据库池推满。先小流量试验并看饱和度，异常时可按版本回退。凭据单独管理，日志记版本和来源即可。

## 什么时候把模块拆成服务

报表查询和导出可以先留在一个应用：路由、业务和存储边界仍能用模块测试清楚。如果导出占用大量 CPU，或需要与查询独立扩容、发布和隔离，才考虑拆出 worker 或单独服务。拆分前写清：谁拥有任务状态，谁负责失败重试，哪个接口保持向后兼容，以及谁监控积压。跨服务会增加网络失败、权限与部署协调；通过另一个服务的数据库直接更新状态，会绕过它的约束和演进边界。

## 踩坑清单

- DNS 能解析只说明有解析结果。发现调用失败时，依次确认目标地址、连接、就绪、协议兼容性和 handler 执行结果。
- 别把存活与就绪绑到同一个依赖上。数据库短时不可用可能需要暂时不接流量；重启所有进程通常不能修复共享数据库，反而会增加恢复压力。
