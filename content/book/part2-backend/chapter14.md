# 第 16 章：缓存、读路径与一致性

报表列表每次刷新都查数据库，用户一多，查询开始排队。前端会用查询缓存减少请求，服务端也可以在查库前读缓存；区别是一个 Redis 键可能被许多实例和用户共同读取。设计缓存时，先决定谁可以读、哪份数据说了算、旧值能留多久，再计算能省多少次查库。

## 先缓存可以容忍旧值的读取

以团队的公开报表模板为例，应用先按团队及模板标识读缓存，未命中再查数据库，回填结果并设置 TTL。这是 cache-aside。数据库是事实源；读到缓存也不能跳过访问控制。如果不同角色看到不同字段，要么按权限范围区分键，要么缓存公共部分，再按当前身份过滤。任务归属和取消资格这类决定副作用的判断，回事实源确认。

更新时，常见顺序是先提交数据库，再删除缓存。仍有两个窗口：删除失败时旧缓存还在；读请求先查到旧值、写请求提交并删键后，读请求可能把旧值填回来。TTL 是控制陈旧时间的手段，不等于强一致；业务要求立即读到自己的更新时，可以让对应查询绕过缓存，或按版本校验后回源。缓存故障时也要控制回源量，否则缓存刚掉线，数据库就会被突增的读流量拖垮。

## 按读路径的承诺选择缓存策略

报表模板列表允许短时旧值，可以先查缓存。用户刚提交后查询本次任务，显示一个旧终态或旧权限判断的代价更高，应走事实源或核对版本。考虑同一时段内的三项量：命中数、读源次数、陈旧读次数。只记录命中会把“读到旧版本”误认为优化成功。

[缓存实验](../../../labs/part2-backend/chapter14/report-cache/README.md)固定读旧值、提交更新和回填的交错顺序。对照走缓存与写后读绕过缓存的结果，再用同一实验的可选真实 Redis 路径核对命令行为。若系统承诺强一致，绕过一部分读取无法替代对所有相关读写路径的约束。

## 区分三种回源突增

| 现象 | 优先验证 | 一种处理方式 |
| --- | --- | --- |
| 大量不同 ID 都查不到 | 未命中后，数据库的空结果是否也增加 | 校验参数，对确定不存在的结果短时缓存；创建后使空缓存失效 |
| 一个热门键到期后大量并发查库 | 回源是否集中在同一个键 | 同实例合并同键请求，或允许短时旧值并在后台刷新 |
| 大量键同时到期或 Redis 故障 | 多个键是否同时回源，缓存错误率是否上升 | TTL 加抖动；对回源设并发上限，保护数据库 |

看缓存命中率时同时看回源 QPS 和数据库等待时间。命中率从 99% 降到 95%，若总请求数不变，未命中流量就会变为原来的五倍。

## 限流和锁回答的是不同问题

限流决定“这个租户此刻还能不能提交”。固定窗口计数实现容易，但窗口交界可能连续放行两个窗口的额度；令牌桶用补充速率控制长期速率，用桶容量决定短时突发额度。用 Redis 做跨实例配额时，计数和首次设过期要作为一个原子操作；分两次调用，进程可能在中间退出。限流依赖不可用时，按接口代价决定用保守的本地额度还是拒绝昂贵写入，并明确本地额度不会自动成为全局额度。

租约锁回答“谁可以暂时尝试刷新”。单 Redis 实例上的典型做法是以唯一持有者标识和 TTL 做原子获取，释放时原子地比较标识再删除。进程暂停超过 TTL 后，另一个实例可能获得租约，旧实例也可能恢复并继续写。标识只能保护释放动作；重要写入仍应由数据库约束、条件更新，或由存储端拒绝过期的递增凭证来保护。

## 踩坑清单

- 缓存连接失败与正常未命中分开记录。若两者都记为 miss，无法判断是缓存策略失效还是依赖故障。
- 限制每秒接收多少请求与限制同时处理多少请求是两个问题：单次执行时间翻倍时，同样的接收速率会占用更多资源。并发保护见[第 19 章](chapter20.md)。
