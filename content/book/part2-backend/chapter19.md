# 第 18 章：超时、结果未知与幂等

用户点击导出，转圈一秒后页面提示网络超时。服务可能还没收到请求，也可能已经建好任务，只是响应没传回来。前端禁用按钮能减少连点，却挡不住自动重试、刷新和另一个标签页。服务端要让同一次业务意图可以安全地再次提交，并让调用方能查到结果。

## 用同一个键找回同一个业务结果

页面为一次导出意图生成一个幂等键，重试沿用这个键；用户主动创建另一份导出时使用新键。服务端从认证信息确定租户和用户，把身份、操作名、幂等键及请求参数摘要关联起来。同键同参数返回同一任务；同键不同参数返回冲突；不同用户不能凭猜到的键查到任务。

以[第 15 章](chapter15.md)的接纳流程为例，唯一约束负责仲裁两个同时提交的请求。任务和幂等记录一起提交，避免“键占住了，任务却没创建”。并发冲突后根据已提交记录返回原任务；处理中按协议返回可查询状态。给幂等记录定义保留期，超过保留期无法保证仍能识别这次提交。业务若永远不允许重复，还需要稳定的业务唯一约束。

## 把超时当作等待预算

页面最多等 800ms，网关预留回包时间，RPC 和数据库共享剩余预算；各层独立再给自己 800ms 会使工作在上游放弃后继续堆积。Go 中让派生 context 继承上游截止时间，传进真正支持取消的 I/O。取消信号表示调用方停止等待或请求停止工作，不能证明远端已回滚。已接纳的异步任务有自己的执行期限和取消协议。

| 观察 | 调用方的选择 |
| --- | --- |
| 输入错误或无权限 | 修正输入或处理授权；重复发送不会改善结果 |
| 短时网络错误，读取可安全重试 | 在剩余期限内做少量退避重试，加随机抖动 |
| 写入超时，提交状态未知 | 用原幂等键重试，或按业务标识查询结果；不要换新键盲重试 |
| 已收到过载拒绝 | 尊重服务端的等待提示（如果有）；预算不够就停止，避免立即重发 |

重试优先集中在能判断业务语义的一层。三层都允许一次重试，最坏可能把一个入口调用变成 2 × 2 × 2 = 8 次最下游尝试。退避只减小短时冲击，还需总时限、次数和整体重试预算。

## 页面收到 503 和没收到完整响应，下一步不同

接纳队列满时，本地 Lab 明确返回 503，并且没有占用任务 ID。页面先等容量恢复，再用原键重试。响应体被截断时，客户端手里没有完整任务 ID，但服务端可能已经提交。此时在页面显示结果未知，沿用原键找回原任务，并对照接纳数、沿用原键数与最终结果。

在 [报表导出综合实验](../../../labs/part2-backend/chapter21/report-flow/README.md)依次跑 lost-response 和 overload，每次从干净进程开始。把第一次返回、服务端是否已接纳、第二次返回的 ID 写成三列。浏览器若只根据 202 响应头开始轮询，就会缺少合法 ID；必须先成功解析完整响应。

## 依赖持续故障时，先减少调用

熔断器按一段时间内的失败率或慢调用比例判断：关闭时照常调用，打开时快速拒绝，半开时放少量探测再决定恢复还是继续拒绝。要有最小样本数，避免一个偶发错误就打开；也要记录拒绝次数和状态变化。熔断保护的是调用链资源，恢复依赖需要另外处理。

降级改变用户能得到的结果。例如模板推荐服务不可用时仍可创建导出；展示旧模板列表时标明更新时间。鉴权失败和任务归属不明不能走“默认允许”的降级。把导出与查询的并发池隔开，慢导出也不容易占满查询资源。

## 踩坑清单

- 把所有超时当成失败并展示“请重新创建”，会诱发重复任务。页面可先显示“正在确认”，根据任务查询结果更新终态。
- 重试前先识别错误类型与副作用；一次重试的收益要和新增负载一起看。
