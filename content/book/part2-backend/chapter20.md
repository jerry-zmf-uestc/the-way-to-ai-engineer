# 第 19 章：并发、背压与过载保护

报表页面单人使用时只要 100ms，活动开始后 p99 涨到几秒，CPU 却没有跑满。前端看到的是响应变慢；服务端可能在等数据库连接、锁、下游响应或空闲 worker。写更多 goroutine 可以增加在途工作，但要提高吞吐，先找到哪个资源不再能按时服务。

## 先算同时有多少工作

吞吐量是单位时间完成的请求数，并发量是某个时刻系统内的请求数，响应时间包括排队和实际执行。稳定区间内，平均在途量约等于吞吐量乘以平均停留时间，三项必须用同一观察边界和时间单位。例如完成 200 次/秒，平均停留 100ms，平均在途约 20；平均停留变成 500ms、吞吐仍是 200 次/秒时，在途约 100。这里使用均值，不能把 p99 代入当成平均并发，也不能套在持续积压的瞬间。

如果每个任务都需要占用一个数据库连接，worker 的上限要结合可用连接数与连接持有时间来定。增加 worker 可能只会把队列从应用挪到连接池。看到 p99 恶化时，先拆出接纳前排队、应用队列等待、数据库连接等待和实际 SQL 执行时间，再选择优化点。

## 让过载有一个能观察到的出口

限速约束进入的速率；并发上限约束同时执行数；有界队列吸收短时尖峰。背压则把“暂时接不动”的信息传给上游，例如消费者减少拉取，生产者暂停或减速。队列满时，交互 API 通常需要尽快返回明确拒绝；用户超额度可以返回 429，服务暂时不可用可以返回 503，客户端要停止紧密重试。后台任务也需要最大排队时间，否则用户离开后仍在花资源做已过时的工作。

[Go worker pool 实验](../../../labs/part1-golang/chapter09/worker-pools/README.md)适合先观察 worker 和 channel 如何交接工作。部署到多个实例时，单实例限制还要乘上实例数，再核对共享数据库和下游的总容量。

## 用压测找拐点，再用剖析解释拐点

先定义用户可感知的目标，比如在某个请求组合下，导出提交成功率至少 99%、p95 小于 300ms，并单独衡量导出完成时间。基线、阶梯增压、短时突发与卸载恢复各有作用。记录发出、接纳、成功、超时和拒绝数，连同 p50/p95/p99、队列深度、池等待和 CPU；成功请求很快但拒绝率大涨，不能算性能改善。固定并发客户端在服务变慢时会自行降低发起速率；要验证外部持续到达的场景，需要固定到达率的负载，且确认压测端未先跑满。

Go 的 CPU profile 回答“CPU 时间花在哪里”；CPU 不高时，先看 goroutine 堆栈和连接池指标，判断是否在等 I/O；block 或 mutex profile 可进一步定位同步等待，需按需采集。heap profile 用于定位堆内存占用或分配热点，记清看的是在用量还是累计分配。对比前后使用同类负载、相同采样窗口与配置，逐次只改一个主要因素。pprof 端点仅在受控环境开放，避免暴露内部运行信息。

## 同一输入速率下，队列长度改变了什么

[负载对照实验](../../../labs/part2-backend/chapter20/report-overload/README.md)按固定的计划到达间隔发送请求，工作槽与合成执行成本保持一致，分别使用大队列、小队列和零等待队列。比较成功请求的 p95、完成吞吐、拒绝比例和最大排队时间，并检查停止发压后新请求是否恢复。

只报成功 p95 会漏掉被拒绝的用户；只报完成吞吐又会漏掉长时间等待。选择队列长度时，先给出端到端等待预算，再估算工作槽能处理的速率。长队列有机会吸收短脉冲，但持续过载只会把问题推迟。若采集 pprof，先用指标判断是 CPU 执行慢还是排队等待，再选对应的剖析手段。

## 踩坑清单

- 单元 benchmark 衡量局部代码，服务压测衡量整条链路；局部更快不意味着请求 p99 会下降。
- 把队列改成无限长会把立即拒绝变成超时和内存增长。卸载后也要观察何时恢复，避免被历史积压拖住。

## 动手练

配套实验：[报表过载：用 503 保护执行容量](../../../labs/part2-backend/chapter20/report-overload/README.md)。先跑故障与修复对照，再完成下面的推演。

| 练习 | 起点与操作 | 检查结果 |
| --- | --- | --- |
| 20.1 找出容量拐点 | 用三组教学数据画对照：发出速率 100/200/300 次每秒，成功速率 100/197/205，p95 为 80/240/900ms；按 99% 成功率、p95 小于 300ms 判断 | 只有第一组同时满足两个条件；后两组还需区分超时和拒绝，不能只看 p95 |
| 20.2 给 worker pool 加过载测试 | 从现有 worker pool 实验出发，在自己的练习副本里用阻塞任务占满 worker，给等待区设上限，再多提交一次；用同步信号控制释放 | 满载时在约定期限内拒绝或返回取消；释放后能接新任务；并发测试通过 race 检查 |
| 20.3 选择剖析证据 | 假定 CPU 为 30%、数据库连接池已满、SQL 自身耗时基本不变、池等待增加；列出先采集的两项证据 | 能区分等待池连接与 SQL 变慢，提出一个可用同等负载复查的假设 |
