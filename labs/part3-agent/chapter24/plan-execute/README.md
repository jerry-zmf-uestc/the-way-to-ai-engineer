# 实验：计划状态、修订与完成证据

固定初始计划先查询retry，再按依赖查询timeout。timeout的初始查询失败，候选计划保留retry完成项并修改未完成查询。只读固定事实、标准库，不调用Planner模型，不实现并发调度或Checkpoint。

timeout依赖retry用于固定演示次序；两个固定查询并不使用彼此的结果，不代表参数间存在业务依赖。正文区分信息依赖、资源限制与展示顺序。

## 故障与边界

- 未知依赖、环、重复ID在执行前拒绝。
- 完成项在候选计划中被删除或改变定义，ErrRevision；不接受原版本再次提交。
- 完成进度与计划快照不向重规划回调共享；执行回调也只取得节点依赖副本。
- 修订次数和总Attempts分别限制，修订不能重置总预算。
- 取消后迟到事实不记completed，工具错误保留原因。
- 所有节点完成但事实不符合目标，独立Complete返回false；不使用清单勾选作为成功证据。

最多16个节点、32次总尝试、8次修订；查询与事实大小另有上限。依赖比较保守，顺序变化也视作定义变化；需要规范化时明确规则。当前状态仅在内存，不提供进程恢复。

## 迁移练习

1. 构造合法但漏掉必要目标的计划，检查“计划完成”与“任务完成”差异；设计执行前覆盖检查。
2. 新资料版本使已完成事实过期，设计显式失效和新节点身份，不能静默修改completed记录。
3. 增加无效修订与空结果反例，确认预算能终止循环；把反思依据写成真实差距，而非模型自信。
4. 用同任务比较ReAct、固定计划和有界修订，保存完成度、执行次数、失败与配置；真实模型对照另设受控调用。
5. 设计并发就绪队列时说明配额、结果顺序、失败传播与取消；不要仅启动goroutine就声称完成调度。
6. 在副本中移除timeout对retry的人工依赖，核对初始就绪集合与执行顺序；解释为什么多个节点就绪并不使当前串行Run自动并发。再增加一个确实需要两份查询结果的汇总节点，说明它的产物和完成条件。

## 最佳实践

## 最佳实践

### 计划状态由证据推进

模型提出结构与修订，应用决定执行和提交。completed有实际产物或有效观察，不能只来自清单更新文本。

### 保持目标与评分答案分离

Planner需要任务要求和允许能力，不需要评估数据中的正确答案。查询目录和工具观察也要说明来源，避免把隐藏标签作为“推理能力”输入。

### 明确重用与失效

版本检查、完成节点身份和证据来源共同决定哪些结果能保留。修改任务要求时重新判断，不自动继承旧计划的成功状态。

### 按信息变化触发修订

发现新依赖、目标漏项或现有动作无法取得证据时，再决定是否重规划。一次可恢复网络故障先按Runtime重试契约处理；没有新信息却反复生成计划，可能只增加费用。保留原计划和触发依据，才能判断修订解决了哪个缺口。

## 常见问题排查

## 常见问题排查

### 所有节点pending，却没有可执行项

先查循环和不存在依赖，再查已失败的前置节点，最后看就绪选择。合法DAG也可能因失败阻塞，需要重规划或终止，不能无条件扫描直到“碰巧成功”。

### 修改计划后重复查询已完成步骤

检查完成节点是否被删除、改名或重新标pending。修订保留定义与证据，重做应有显式失效原因；不要在每次修订时清空全部进度。

### 清单全完成，答案仍漏项

对照任务要求而不是计划自身。缺失目标、错误事实或冲突都应由独立完成检查识别；再修Planner的分解规则和反馈，而非直接放宽评分器。

### 两项无关查询被强制串行

逐条检查Depends是否承载实际数据或业务前置；仅为列表排列而加的依赖，不应被误当作事实关系。移除人工顺序后先验证就绪集合，再由调度器处理资源限制；不要直接删除所有依赖或跳过执行前校验。
