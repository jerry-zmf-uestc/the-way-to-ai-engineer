这本书把正文和示例代码放在同一个仓库中，学习记录由你保存在自己的笔记里。正文在 `book/`，示例在 `labs/partN-主题/chapterNN/示例名/`。每章的示例索引可以直接打开源码，不需要另外下载一份练习工程。

## 从一个能回答问题的页面，看清整条学习链

你想做一个资料问答助手：用户输入问题，系统查找资料，生成带来源的回答，并允许中途停止。AI 可以很快生成页面、Go handler 和模型调用代码。困难出现在第二天：答案引用了不存在的文档，网络断开后任务重复运行，用户按停止后后台还在消耗资源。代码看起来合理，却没人能说明失败发生在哪一层。

本书围绕这种判断能力组织学习。你需要看懂一条链路：用户输入经过 HTTP 进入服务，Runtime 组装消息，模型提议动作，应用校验并执行工具，资料作为证据返回，答案经过检查再交给界面。Go 的 map、接口、error、channel 和 context 在这里都有具体职责；数据库、缓存、队列与 RPC 则处理持久化、通信和负载。知识只有连到这些职责，才能在换框架或换模型时继续使用。

先打开[第33章的流式资料问答](/the-way-to-ai-engineer/chapters/agent-serving/#topic-ch32-streaming-service)。这个独立 Lab 不需要模型密钥，用固定资料和 fake 展示一次完整请求。能跑通之后，沿着问题回到第24章的执行循环、第9章的取消和第10章的 HTTP。还不会 Go 时，先看页面和链路，再从第1章开始建立语言基础。

## 工作流、Agent 与支撑它的系统

固定工作流由程序决定下一步，例如每次都先检索，再生成，再校验。Agent 循环允许模型根据观察提议下一步，应用仍决定是否执行。两者可以组合：把开放决策放在一个节点里，外围使用固定流程限制输入、预算和输出。对于步骤已知的资料问答，固定流程通常更容易验证；只有任务确实需要动态选择工具或调整计划时，才增加开放循环。

模型接口解决“如何发起一次推理”；Runtime 解决“运行如何推进、记录、停止与恢复”；框架提供组件和组合方式；Harness 可以把文件、工具、策略、上下文管理与评估组织成适合特定任务的工作环境。这些词在不同项目中会重叠，不能仅凭名称判断能力。读源码时要问：谁保存状态，谁持有权限，谁处理超时，谁判断完成？

一个能输出工具调用的模型，不自动拥有工具权限；一个提供消息历史的框架，不自动提供可靠 checkpoint；一个展示流式文本的页面，不自动证明后台任务已成功完成。课程中的 Lab 把这些相邻概念拆开，让你能单独测试每一层。

## AI 做准备，你做预测与判断

AI 很适合整理概念地图、定位源码、生成候选方案和构造测试输入。是否可以少读、跳读，取决于接下来要做的判断：查一个 API 可以检索；决定重试策略则要认真读错误语义、提交边界和失败案例。涉及状态、权限、并发和数据一致性时，不能靠摘要代替关键源码。

每次学习使用一个小循环：

1. **提出具体问题。** 例如“停止页面连接后，哪个 context 会取消？”把问题写到可验证的程度。
2. **先预测。** 不运行、不让 AI 给答案，画出调用顺序，写出返回值、状态变化和可能失败点。
3. **查最小必要内容。** 读对应正文、函数和官方资料，请 AI 解释不懂的部分，再回源码核对。
4. **运行并制造一个故障。** 改一个参数、预算或错误输入，观察预测与实际哪里不同。
5. **合上材料解释。** 用自己的话说明机制，换一个输入或场景再预测；解释不清时回到那一层补读。

可以这样请求 AI：“给我三个输入，让我先预测运行结果；等我回答后再指出遗漏的边界，并给出源码位置。”让 AI 直接完成练习也能得到产物，但会失去诊断你是否理解的机会。每周至少保留一次不用 AI 的短实现或故障解释，用来发现知识缺口。

笔记保存问题、原先预测、实际结果、修正后的解释和一个迁移用例。全文摘要只在它能帮助找回资料时保留。读完很多内容并不是终点；能够解释失败并把机制用到新任务，才有继续推进的依据。

## 按基础选择阅读路线

| 路线 | 顺序 | 进入下一步的依据 |
| --- | --- | --- |
| 前端工程师，Go 与后端基础尚不完整 | 先体验第33章 → 第22–24章 → 第9、10章 → 第1–8章 → 第27章 → 后端正文 | 能把页面上的输入、流式输出、停止按钮和来源展示，分别对应到 HTTP、context、Tool、Runtime 与 RAG 证据边界 |
| 已有后端经验，Go 需要补齐 | 先体验第33章 → 第22–24章 → 按缺口补第2、5、7、9、10章 → 第27章 → 后端与 Runtime 深化 | 能自己写一个可取消、可测试的工具执行器，说明权限与错误边界 |
| Go 与后端基础尚不完整 | 第1–8章 → 第9–11章 → 后端正文 → 第22–24、27、33章 | 能解释值与引用、错误传递、接口、取消和 HTTP 生命周期 |
| 已做过 Agent/LLM 应用，想系统补运行治理 | 先读构建篇的架构、受控行动、决策循环、上下文与RAG，再进入运行时的 Runtime / Checkpoint / Multi-Agent / Serving，最后用治理篇补观测、评估、安全与成本 | 能把一次任务拆成输入、决策、执行、观察、评分和终态，并说明每层失败该在哪里排查 |

章号表示正式主题位置，阅读顺序可以按能力依赖调整。目录只链接已有正文，不把规划中的标题当成现成教材。全书规划涉及更深的恢复、调度和评估；入门切片不要求先掌握所有这些机制。

如果每周投入8–12小时，可把一个机制安排为一周：约2小时建立问题和阅读关键段落，3–4小时运行与改代码，2小时故障与测试，1小时闭卷解释，剩余时间补基础或延伸。内容较难就跨两周，不按章数赶进度。最初四轮可以依次完成 Go/JSON与接口、消息与结构化输出、工具与循环、SSE与取消；资料检索随后加入。基础诊断发现缺口时先补齐，不能用“已经运行成功”跳过。

## 什么证据能够证明什么

| 证据 | 能支持的判断 | 仍需验证 |
| --- | --- | --- |
| 固定数据与 fake 测试通过 | 数据、协议、权限和错误路径按约定执行 | 真实模型的选择和回答质量 |
| 来源 ID 与摘录校验通过 | 回答中的摘录确实来自本次检索结果 | 资料真实性、相关性和自由生成断言是否被支持 |
| 一次真实模型演示成功 | 这次输入在这个模型版本下成功 | 数据集上的稳定性、成本、延迟和失败分布 |
| 学习者完成故障解释与迁移题 | 能在该任务中使用机制 | 新场景和生产规模下的能力 |

因此学习要先验证确定性底层，再接真实模型；评估要固定任务和评分规则，记录失败案例。页面是否漂亮、答案是否流畅、测试是否全绿，分别回答不同的问题。

## 运行与练习

### 环境与工作目录

示例要求 Go 1.26.6 或更新的兼容版本，最低版本以 `labs/go.mod` 为准。命令默认从 `the-way-to-ai-engineer` 仓库根目录运行，先执行 `go version`，再确认当前位置有 `package.json`、`book/` 和 `labs/`。

后端和 Agent 示例还依赖 `labs/go.mod` 锁定的第三方包，首次运行前联网执行 `go -C labs mod download`；依赖缓存准备好后，默认测试无需访问远程模型或数据库。

单个示例只需要 Go 和该示例注明的运行条件。若要运行全仓 `make validate`，还需要 Node 22、npm、Ruby、make、POSIX shell、ripgrep，以及 race 检查使用的 C 工具链；准备方式见[贡献指南](https://github.com/jerry-zmf-uestc/the-way-to-ai-engineer/blob/main/CONTRIBUTING.md#validation)。不要把维护整本书和构建课程站点需要的工具误当成开始第一个 Go 程序的前提。

课程站点的正文仍来自 `book/`。维护者首次构建站点时运行 `npm ci`，随后执行 `npm run dev` 本地预览，或用 `make validate-site` 完成内容清单、生成器反例和正式构建检查。`src/content/chapters/` 是构建产物，不要直接修改。

### 运行与测试

正文中的 `go -C labs run ./...` 运行一个 Lab，`go -C labs test ./... -count=1` 执行其测试。测试输出中的运行时间和机器路径可以变化，重点看退出码和测试结论。还没学过测试语法时，可以先按章节说明运行现有测试。

正文的命令在仓库根目录执行，例如：

```bash
go -C labs run ./part1-golang/chapter01/hello-world
go -C labs test ./part1-golang/chapter01/hello-world -count=1
```

完整测试使用：

```bash
GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off go -C labs test ./... -count=1
```

“离线”指不访问远程依赖和服务；HTTP/RPC 集成测试仍可能在本机回环地址监听端口。若系统禁止监听，先读对应 README 区分纯函数测试与本地集成测试，不要把环境限制误判为业务错误。

### 第 1、2 章的练习副本

示例的故意失败操作与练习在副本中进行。以下为 macOS/Linux shell 命令；`mktemp` 返回的位置每次不同，只用于本次操作。

```bash
practice_dir=$(mktemp -d)
cp labs/go.mod "$practice_dir/go.mod"
cp -R labs/part1-golang/chapter01/hello-world "$practice_dir/hello-world"
cp -R labs/part1-golang/chapter02/arrays-slices "$practice_dir/arrays-slices"
cp -R labs/part1-golang/chapter02/maps "$practice_dir/maps"
cd "$practice_dir"
```

复制完成后不再使用仓库中的完整 Lab 路径。现在运行 `go run ./hello-world` 或 `go test ./maps -count=1`。练习和故意失败操作都在副本中完成，原仓库文件不受影响。

每组独立实验重新从仓库根目录复制一份。连续练习按章节顺序使用同一份副本。不要把故障实验的错误代码带到练习起点。完成后可保留副本复盘，`/tmp` 下数据不适合作为长期笔记。

Windows 用户可在临时工作目录手动复制同样的文件和三个目录，再在该目录执行同样的 Go 命令；上面的 shell 初始化步骤只验证了 macOS 环境。

### 后续章节与分层工程

上面的扁平副本只适用于第 1、2 章的标准库练习。其他章节统一保留仓库中的 labs 路径；尤其 cmd/internal 工程的 import 包含完整 module 路径，不能只复制 cmd 或随意改变层级。

从仓库根目录准备一份完整示例副本：

```bash
practice_dir=$(mktemp -d)
cp -R labs "$practice_dir/labs"
cd "$practice_dir"
```

此后可直接执行正文中的 `go -C labs run ./...` 与 `go -C labs test ./...`。首次使用第三方依赖先联网执行 `go -C labs mod download`，之后用 `GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off` 验证离线运行。review-cli 必须提供 -item 参数，完整命令见它的 README；无参数报错是预期输入校验，不是运行环境故障。

修改 IDL 的练习还需要指定版本的生成工具，按对应 README 在副本中操作。现有示例已经提交生成代码，普通运行和测试不需要重新生成。真实模型和数据库不在默认练习命令中启用；本机回环 HTTP/RPC 测试仍需要监听权限。

### 区分完整程序、摘录与错误示例

“源码摘录”应放回指定上下文，不是独立程序。“完整程序”可以保存成单独文件后执行。“错误示例”预期失败，错误文本可能因工具链版本不同而略有差异。教材中的完整程序可以在练习根目录保存为 `inspect.go`，用 `go run inspect.go` 运行；每次替换该文件内容，不把多个 `main` 放进同一个包。

章节中的 `<!-- verify:... -->` 是维护者验证标记，普通阅读可以忽略。测试脚本据此提取正文代码，避免另存一份示例后与正文分叉。

### 完成练习后检查什么

练习代码块会标出文件、任务和预期结果。省略 package/import 或函数剩余部分的块是摘录，不能直接覆盖整个文件。每题从新副本开始；题目明确写“接着上一题”时再沿用修改。第 1、2 章另有连续题的具体约定。

改函数签名后，连同 main 和测试调用一起检查。故意失败的练习只在副本操作；恢复后再跑已有测试。遇到 Go 代码中的 `TODO`、`panic("TODO: ...")` 或 `t.Fatal("TODO: ...")`，它们用于标出未完成的位置，不是最终实现。
