# 技术文章写作

共用文章生产能力：理解读者与任务、整理材料、局部改稿、规划视觉、提炼判断并检验读者能否理解。技术章节可用机制地图，产品稿可用真实任务与操作推进；不同渠道共享方法，不共享固定目录。

## 定位任务与渠道

从本文件所在目录向上三级定位仓库根目录。读取AGENTS.md及目标路径适用的规范，检查工作区差异，保留现有修改。先从当前请求与原稿确定主题、读者、核心问题、输出位置和允许的编辑范围；能推断的信息直接沿用，关键范围不清时才询问。

| 请求 | 产出与范围 |
| --- | --- |
| 先规划／只给大纲 | 给出技术拆解、章节逻辑、核心主张与所需证据；不修改正文，不自动开始实施 |
| 编写／重构／按反馈修改 | 在已授权路径落实改稿；普通写作请求不增加一轮强制大纲确认 |
| 审查／评价 | 给出定位到段落或标题的问题及修正建议；未要求修复时不直接改稿 |
| 公众号编排中的技术结构复核 | 只读指定输入，在编排者提供的私有工作区输出候选与差异；正式采用、状态及投递仍由编排者处理 |

按渠道加载必要约束，不能将另一渠道的样式或状态流程带入：

- **课程**：完整读取[章节规范](../../../docs/rules/book-chapter-contract.md)、[章节模板](../../../docs/templates/book-chapter.md)；内容审查另读[审查表](../../../docs/templates/book-chapter-review.md)。路径、页面身份、Lab关联和既有锚点以项目清单及规则为准。
- **AI 产品观察**：读取[专用栏目规范](../../../docs/rules/ai-product-observation.md)，接受调用方已确定的体验任务、材料身份和范围；使用共用方法，不反向调用产品Skill，不套用AE题库、课程机制目录或设计者问题主线。
- **面试栏目公众号技术稿**：按AGENTS.md完整读取面试与公众号规则、模板；已有[公众号编排入口](../agent-wechat-artifact-writer/SKILL.md)传入的题号、候选目录与事实保护项继续有效。本Skill不反向调用该编排入口，不递归启动生产流程。
- **图示或Lab变更**：仅在请求确需时加载对应图示/Lab规范，不因文章提到代码或配图就扩展为新工程或重画素材。

## 作者偏好与持续学习

起草、改稿和内容审查先读[当前作者偏好](references/author-style.md)，只应用适合当前渠道与任务的条目；缺少样文时不补造完整作者画像，外部媒体仅作参考。

遇到新增认可资料、成稿采用、持续偏好、整理经验或回退请求，读取[写作学习与编译](references/style-learning.md)和[验证与回退](references/style-evaluation.md)。先标识材料身份与认可范围，再记录、提炼、合并/修正规则并验证；共用方法、作者画像与渠道要求各维护一份。只在当前任务内执行，不启动后台学习或自动改模型参数。

## 共用协作与视觉模块

开始写作、改稿或审查时读[协作改稿与读者检验](references/collaborative-writing.md)。上下文已足够就直接完成，不按固定问卷逐节确认；作者直接改文与自然语言反馈同样有效。

散文起草、重构或用户要求去AI味时读[具体细节与自然行文](references/concrete-prose.md)：用可核对的细节和动作承接用途与判断，减少重复表态和空泛过渡；既有章节组织与证据范围继续有效。

文章需要头图、截图、示意或用户反馈缺图时读[图文规划与交付](references/article-visuals.md)。先判断图片应证明什么，再选择截图或插画；本模块能独立服务封面任务，不连带技术重写。按需生成图片，不把图片数量当质量指标。

来源与适配关系见[方法来源说明](references/method-sources.md)。这里吸收doc-coauthoring的材料收集、局部迭代、读者检验，以及baoyu-article-illustrator的图位分析和类型×风格×配色；这是项目适配，不安装或整体调用上游工作流。

## 技术解释型文章：先拆体系，再放入案例

以下结构仅用于机制解释型文章，不强加给产品观察或体验稿。先形成一份简短的内容蓝图：核心问题、主要构件或机制、相邻概念边界、读者需要作出的判断，以及每项判断所依赖的代码、图或来源。已有材料足够时直接利用，不先重新研究整个领域。

H2表达职责明确、粒度相近的技术模块；H3展开其数据模型、操作过程、约束或取舍。目录应能让读者看出技术如何分解和组合。不要只用“为什么／是什么／怎么用／总结”包住所有内容，也不要把每个段落都升级成标题。编号遵循原稿或渠道约定。

区分概念地图与运行路径：前者解释组件关系，后者解释一次调用或状态变化。选择最符合主题的组织方式；需要说明流程时写清输入、操作主体、状态变化、输出与失败出口。存储选型、缓存一致性和模型质量等不同层的问题应分别讨论，再说明交接关系。

案例用于给机制提供具体输入与观察。比较多种方案时尽量沿用同一任务和约束，说明比较维度；不要把同一段案例反复讲述，也不把新增场景当作技术分解。构思或重构大纲、提炼结论时，按需读[结构与结论示例](references/structure-and-conclusions.md)。

## 把关键机制讲到可判断

围绕本节要解决的问题，选择必要的解释、示例和证据；避免先罗列全部校验细节，再交代机制的用途。首次出现的术语就地解释，不依赖读者记住后文定义。

- **解释职责**：指出决定由模型、宿主应用、执行器还是存储承担。格式、权限、内容真实性与任务效果分别判断。
- **解释代码**：代码前交代是完整程序、源码摘录、教学示意还是失败例；代码后解释关键分支或状态为何这样设计。复用课程Lab摘录时保持源码一致，不凭空补出尚未实现的能力。
- **解释图示**：先确定图要表达的关系、时序或状态，图与正文使用一致名称。图旁说明它支持的判断，图片不可见时正文仍能理解；现有合格图直接复用。
- **解释取舍**：讲清方案在什么条件下成立、增加什么代价、失败后调用方如何处理。把取消、冲突、授权或失效放在相关机制附近，不堆成文末通用清单。

动态产品行为、版本化API和有争议主张回到官方资料或可定位原始来源。证据保留与引用呈现分开：课程和每日一题遵循各自引用规范；AI产品观察的核查台账另存，读者正文不加来源编号或参考章节。已有实验记录可以引用，但保留原任务、版本、失败和限制，不冒充本次新运行；自动测试、模型对照、内容审校和真人阅读效果分别报告。

研究不足时可按需使用当前环境已有的content-research-writer，纯中文编辑可使用humanizer-zh；先读实际入口再遵循说明，不虚构技能调用命令，不因本Skill自动安装社区依赖。没有这些辅助Skill仍可依据项目规则完成技术写作，明确实际使用的能力。

## 提炼并呈现关键结论

在解释足以支撑判断的位置，提炼读者能带走的结论：谁负责什么、何种条件下选择什么、哪项检查保证什么。保留成立条件与适用范围；避免“很重要”“要注意”“更可靠”等无法指导判断的强调。

只突出承担核心判断的句子，不整段加粗，不给每一小节强制添加口号，也不把已有加粗小标题当作结论。强调数量由信息价值决定。

- **课程**：可使用独立引用块加粗突出关键工程判断，段内重点使用普通加粗；不另造“本章核心”等仪式性栏目。
- **公众号**：复用结论的语义，样式交给公众号规则与排版阶段；沿用同字号、青绿、无底色要求，不自动搬入课程的引用块外观。

润色时删去重复解释与无信息过渡，保留术语、否定、数字、代码、来源和确定程度。简洁不能通过删掉关键条件、失败路径或必要证据来实现。

## 复核与交付

先检查读者能否顺着目录回答核心问题，再检查代码、图示、术语、引用和结论是否相互支持。重构时逐项核对原知识、练习、来源与有效链接的去向，保留作者已确认的删改，不用字数、标题数或高亮数代替审查。

按AGENTS.md及本次改动类型运行现有验证：文档变更运行文档检查，代码摘录或操作变化执行相应书稿与示例检查，呈现变化执行站点检查。缺工具或既有问题阻断时报告具体范围，不修改无关文件来制造通过。

交付说明实际产物、关键结构变化、运行的检查及仍缺的证据。用户只要方案时交付方案；用户已授权改稿时完成改稿。公众号嵌入调用返回明确候选文件、差异与检查结果，不更新正式稿、题库状态或远端草稿。提交、部署及平台操作不包含在技术写作授权中。
