# the-way-to-ai-engineer 项目总体方案

本文档是项目愿景、课程结构、职业路线、仓库架构、章节状态、交付方式和长期边界的唯一设计入口。它描述当前有效方案，不保存迁移过程、已经完成的阶段计划或互相竞争的目录草案。

目标课程按37个教学单元规划，其中Go与后端保持1–21章；Part 3包含16个教学单元，对外按三大篇组织：构建篇、运行时、治理篇。九类Agent知识体系继续作为内部蓝图和内容审查维度。目标主题使用语义ID追踪，单元编号在清单中维护，Part 3源码文件号与教学单元号保持一致。当前已将Harness纳入编号正文，Eino独立章节退出课程主线；下一阶段逐项核对蓝图、技术深度、模型效果与读者证据，不能由篇目齐全直接宣称课程完成。章节页和首页按同一三大篇分组；章节清单已建立37单元映射与展示编号，后端10章均有阅读入口，独立实验的实现状态仍在章节地图中单独跟踪。第4节按现有33个章号记录真实状态，补充正文归入对应行，但不能继承同一行其他主题的验收结果。第3节定义目标结构，正文完成、机制测试通过、模型效果成立、读者学会与公开发布分别验收。

具体写作、Lab 和安全要求分别由 `docs/rules/` 维护；实际命令以根目录 `Makefile`、`package.json` 和 `labs/go.mod` 为准。

本方案落实的课程质量基线：**一篇正文聚焦一个工程问题，按主题拆解知识点，用代码与图示讲清机制，再由独立实验验证。** Agent Loop样章提供深度与表达的参照，其他章节依据自己的状态、协议和设计问题组织内容，不复制样章标题或段落结构。样章确定的约束及其执行入口见第7节，实施优先级见第11节。

规则已同步到[章节规范](../rules/book-chapter-contract.md)、[章节模板](../templates/book-chapter.md)、[章节审查表](../templates/book-chapter-review.md)和[AGENTS.md](../../AGENTS.md)。本方案负责课程目标、主题蓝图、实施次序和完成判据；专项文件负责写作、实验与验证的执行细节。规则同步只表示建设依据一致，每篇正文仍须核对知识覆盖、代码与图示、实验行为和学习效果，不因采用样章形式而自动通过。

Part 3用最小决策闭环串联知识：先理解模型提议、应用执行、观察回填与终止，再定位各扩展如何改变信息、决策、控制权或运行约束。课程建设同时回答“怎样实现”和“何时值得采用”；运行稳定性、任务效果与学习效果分别验收，不能以接入更多部件代替质量提升。

**课程的贯穿问题：一个Agent怎样根据有效资料完成任务，并在信息不足、工具失败或执行中断时作出可靠选择？** 新机制沿这条任务链定位：进入模型的输入、模型提出的动作、应用执行边界、观察与状态更新、继续或终止、最终交付。先找出需要改变的位置，再学习机制、验证效果；框架重组控制流时，也沿同一任务核对职责变化。各Lab保持独立启动，知识之间通过输入输出、状态和判断串联。

下表是后续建设与修订的共同依据。具体主题蓝图见第3节，写作与审查要求见第7节，实施顺序见第11节。

| 决策 | 实施方式 |
| --- | --- |
| 按核心部件组织课程 | Part 3 对外按构建篇、运行时、治理篇组织，内部按九类Agent知识体系审查内容；同一任务链中的相邻部件合章，内部区分职责；Tool与Loop继续分章 |

| 保留递进，允许不同结构 | 顶部固定“配套实验”，文末固定“小结”“参考文档”；主体标题根据本章的机制与问题命名，最佳实践和常见问题排查按复杂程度设置 |
| 代码、图与文字共同解释 | 关键代码呈现决策条件、状态更新和失败分支；图示解释职责、顺序或状态；文字说明原因和取舍。完整工程、启动命令、测试导读与练习放在独立Lab |
| 让步骤与判断可辨认 | 有顺序的动作拆成步骤，写清输入、变化与分支；值得记住的工程判断适度高亮。小结提炼3–5个已讲清的要点，再引出下一篇承接的问题 |
| 保持自然、准确的技术表达 | 删除套话、重复提醒和维护口吻；源码出处与片段性质就近说明，有歧义时再补充。保留影响理解的前提、错误语义与边界 |
| 用证据判断课程质量 | 分别验收主题覆盖、机制行为、任务效果、复杂度收益和读者迁移能力；采用参考课程的布局或通过自动检查，不能据此认定质量相当 |

这些决策落实到方案、规范和模板，不意味着所有正文已经符合要求。修订时逐章核对，不批量套标题或统一句式；原知识点、练习、来源和能力验收要求继续保留。

## 1. 产品定位

项目以 Go 为核心 Runtime 和后端语言，构建一条从语言基础、高性能后端到 Agent 系统工程的连续学习路径。课程正文负责解释机制和设计取舍，独立 Lab 负责运行、测试、故障复现和指标观察；content/interview/ 提供框架中立的 Agent 面试合集及公众号内容生产，Astro 当前只发布课程阅读体验。

第一目标用户是已有 TypeScript/React 经验、希望补齐 Go 后端与 Agent 工程能力、并形成可验证作品证据的前端工程师；其他已有软件工程经验、准备系统进入 Go AI 全栈方向的开发者也适用。TypeScript/React 主要承担 Console、Trace、Replay 和 Eval 界面；首个 Console 采用无构建的原生 JavaScript，先验证协议与生命周期，再逐步扩展浏览器侧可见面。Python 只承担必要的 AI 生态互操作和框架对照，不重复实现 Go Runtime。

六个月目标是达到高级 Agent Fullstack / Runtime Engineer 的可面试水平，并形成 AI 架构设计基础。课程完成不能替代真实生产流量、事故处理、跨团队协作和长期演进经验，因此不承诺仅凭学习项目达到 Production-proven AI Architect 或 Staff/Principal 水平。

核心价值：

- 把分散的 Go、后端和 Agent 知识组织为一条递进路线；
- 每个关键概念都有可运行、可测试、可解释的独立实验；
- 默认使用 fake、固定数据和显式失败路径，真实 Provider 通过受控 E2E 启用；
- 用 Trace、Eval、故障注入、成本和架构决策证明能力，而不是只展示成功演示；
- 教材、代码、来源、发布和安全边界能够公开审计。

明确不做：

- 不设置毕业设计，不维护一个跨越全部章节持续演进的平台；
- 不创建与 `content/book/` 平行的 `course/` 正文；
- 不用前端视觉完成度代替 Runtime、可靠性和评估质量；
- 不把模型预训练、完整 RL Infra 或 Kubernetes 平台工程设为主线；
- 不实现学习推送、打卡、自动复盘或个人学习记录管理；
- 不实现旅行预订、支付、消息发送等不可逆业务工具。

### 框架策略

Go 主线采用自研最小 Runtime：先理解状态、调用和错误语义，再判断是否需要接入框架或外部协议。框架对照不再作为独立必修章节；如在RAG、MCP或其他局部实验中保留接口对照，重点仍是核对状态模型、扩展点、Memory、Trace、权限和失败行为，不复制开发多套产品。

### 算法策略

算法不单独堆成刷题课程，而是进入真实机制：调度使用堆、队列、DAG 和拓扑排序；缓存使用 LRU/LFU；分布式主题使用一致性哈希、限流和退避；规划使用有界图搜索；RAG 解释向量相似度和近似检索。面试所需的通用数据结构与算法仍需学习者在课程外持续练习。

### 能力边界

独立 Lab 可以证明机制实现和工程判断，不能证明系统已经承受真实业务规模。课程结束后若要竞争生产型架构岗位，还需要至少一种外部证据：真实 AI 产品经历、持续开源维护、真实用户使用、线上故障与容量记录，或跨团队架构落地。

## 3. 课程与作品结构

课程只有一个正文入口 `content/book/`，每篇教学正文关联明确的配套实验。机制Lab围绕一个问题独立运行；集成Lab可以被多篇正文引用，不强求正文与Lab严格一对一：

```text
content/book/                       labs/
连续、自然的技术正文   →   独立运行的机制实验或模板应用
                                  │
                                  ├── unit / integration / race
                                  ├── eval / adversarial cases
                                  └── trace / benchmark / failure evidence
```

三个 Part 的职责：

| Part | 课程范围 | 目标 |
| --- | --- | --- |
| Part 1 · Golang | 1–11 | 写出结构清晰、错误显式、并发可控并具有测试的 Go 程序与 HTTP 服务 |
| Part 2 · 高性能后端 | 12–21 | 理解数据、缓存、通信、容错、高并发和可观测性如何组成可靠服务 |
| Part 3 · Golang Agent | 构建篇、运行时、治理篇；16个教学单元 | 构建、约束、测试、评估并服务化 Go Agent 与多 Agent Runtime |

课程不维护统一结业平台。需要组合机制时，使用以下四类相互独立的作品级 Lab，每个都能从干净环境单独启动：

1. **Agent 推理与恢复**：ReAct、Plan-and-Execute、Reflection、参数修复、重试、取消和预算对比。
2. **Memory 与高级 RAG**：短期上下文、PostgreSQL、Redis、Vector Store、混合召回、HyDE、重排和引用评估。
3. **多 Agent 调度**：角色路由、DAG、Handoff、冲突、死锁、配额、背压和失败传播。
4. **Eval 与可观测性**：Trace、Replay、版本化数据集、质量/效率/成本指标和回归门禁。

四类作品的整合从已经讲清的机制开始，不另设毕业平台。第4类新增独立 `labs/part3-agent/chapter33/eval-observability/`：固定只读任务实际运行后记录调用轨迹，同一配置与资料版本下离线重放，再按Run与Case身份评分，输出回归门禁。Schema2已将工具错误纳入逐调用记录与严格重放，Schema3绑定两次工具尝试上限，对照首错后恢复与耗尽；重放消费原失败及响应，不调用工具或扩大预算。报告区分成功响应、实际尝试与重放核对；旧失败摘要保持未完整验证，执行失败不能被平均分抵消。当前为即时只读重试，退避与进程恢复预算仍待实现。首批四条合成契约任务用于检查记录、重放与评分的交接，不充当已校准的独立模型基准；真实模型质量、usage成本、100合格案例以及其他三类作品继续按原要求建设。公开归档只存本实验合成资料，归档校验不能冒充来源认证或生产审计。

作品级验收与机制实验分开维护：

| 作品类别 | 当前入口与整合状态 | 作品验收的剩余范围 |
| --- | --- | --- |
| Agent推理与恢复 | [策略对照](../../labs/part3-agent/chapter24/strategy-comparison/README.md)、[Checkpoint与固定联合恢复](../../labs/part3-agent/chapter25/checkpoint/README.md)；固定动作已有执行/费用交接 | 扩展到动态决策、修复与策略比较，补真实效果、完整故障交接和作品验收 |
| Memory与高级RAG | [Memory](../../labs/part3-agent/chapter27/user-memory/README.md)、[检索](../../labs/part3-agent/chapter28/neural-retrieval/README.md)、[回答验证](../../labs/part3-agent/chapter28/evidence-answer/README.md)等独立入口 | 所选存储、更新/过期、多路召回、HyDE、真实重排、联合生成及人工评分的同任务证据 |
| 多Agent调度 | [Delegation](../../labs/part3-agent/chapter31/delegation/README.md)、[DAG](../../labs/part3-agent/chapter31/dag-scheduler/README.md)等机制入口 | 真实角色效果、路由与共享配额、跨实例Handoff/恢复、故障及持续流量公平性 |
| Eval与可观测性 | [集成Lab](../../labs/part3-agent/chapter33/eval-observability/README.md)已建立执行→归档→重放→评分→门禁的固定链路 | 真实模型与失败usage、语义评分校准、采集/导出边界、规模与合格数据覆盖 |

入口可运行不自动标为作品完成。各类作品保留原能力范围；累计100合格案例、两阶段真人反馈与六个月路线仍按第9、10节单独验收，不由固定链路或分类标签补记通过。

Eval/可观测性集成另有Schema4逐调用回报契约：来源区分应用、工具、固定替身、真实模型与合成模型计数，版本及usage来源随调用归档；失败与取消保留已回报量，未知不填零。合成计数单列，不改变真实UsageKnown或CostKnown；旧格式不能补造元数据。ObservedDriver的合同和离线重放已验证；最终阶段已通过既有公开CLI实际调用锁定1.7B四次，输入859/输出114，固定任务2/4通过，两个空证据拒答因尾随字符协议失败，门禁拒绝。原文/messages/用量与适配保存，应用选择/工具各4次不算模型调用；动态模型策略、价格/失败账单及完整作品仍按原范围接入，不能将来源声明当认证或用固定数字证明费用节省。

同一集成入口另有Schema5协议修订配置：每Case最多两次最终生成，只对answer_protocol追加稳定反馈，不修补原文、不提供期望值、不重跑工具。实际六次生成仍2/4通过，两个空证据任务重复尾随字符，门禁拒绝；总输入1405/输出152，相比单次多两次及546/38Token，无当前任务收益。归档绑定原上限并重放全部失败，预算不同不声称同调用配额优势；独立任务、真实费用及语义校准继续保留原缺口。

### 四类作品怎样从机制实验走向完整任务

作品建设先确定用户任务、部件交接和失败出口，再组合实现。下面是待实施的任务设计，不是新增案例、已实现接口或验收结果；具体topic路径与命令在实现时登记到章节地图。四类作品仍使用现有Lab目录和共同module，各自准备资料与临时状态，不读取其他实验遗留的数据库、归档或工作目录。

| 作品 | 贯穿任务与最终交付 | 需要组合的关键机制 | 必须保留的比较基线 |
| --- | --- | --- | --- |
| Agent推理与恢复 | 根据多份服务资料回答运行配置问题；遇到只读工具暂时失败或进程中断后继续，交付有来源的完整答案或明确未完成原因 | 动态Loop、ReAct/计划、分类恢复、累计预算、Checkpoint与最终任务评估 | 同任务的固定流程、无反思策略与不恢复运行；分别比较质量、实际尝试、恢复时间与全部消耗 |
| Memory与高级RAG | 根据当前有效资料和用户已授权偏好回答问题；资料更新、偏好到期或撤回后，答案重新判断 | PostgreSQL事实源、Redis候选缓存、长期记忆检索、混合召回、HyDE、真实重排、多引用生成与支持判断 | 词项检索、向量检索、混合检索及逐项增加HyDE/重排；相同资料池、版本和评分依据，拒绝把预置候选顺序当检索基线 |
| 多Agent调度 | 将跨资料核对任务分给不同能力角色，处理依赖、冲突与后台更新，汇总全部必要证据；执行者退出后由新实例按契约接续 | 应用路由、角色权限、DAG、共享预算、Handoff、父子版本、取消、持久归属与恢复 | 单Agent、固定角色流程与协作策略；相同工具/信息范围和总预算，记录路由失败与协调开销 |
| Eval与可观测性 | 对上述任务的两个配置形成可追溯报告，定位退化并作出放行或拒绝决定 | 原始执行记录、Trace关联、严格Replay、独立评分、数据版本、usage/价格来源与门禁 | 保留原配置逐Case结果；同时比较质量、关键失败和消耗，不能只比较平均分 |

不同作品可以采用同一公开合成任务家族以便比较，但每个作品要有自己的完整入口与资料初始化。复用任务不增加案例数量。真实模型、真实存储和框架对照依照各自门禁启用；固定替身负责默认契约回归，不能代替完整任务效果。

#### 集成前先明确交接契约

| 交接 | 应用绑定并核对的内容 | 失败时怎样结束 |
| --- | --- | --- |
| 决策→工具→观察 | Run/Step/ToolCall身份、批准能力、参数、实际尝试与原结果 | 普通工具故障进入有界恢复；权限、取消和协议错误按各自终止语义处理，不混作可无限修复的提示 |
| 执行→Checkpoint→恢复 | 任务/资料/策略版本、所有权、游标、已提交结果、在途动作与剩余预算 | 未知提交窗口保留unknown；只有应用批准的只读重做或可信结果核查才能继续，重启不能清零尝试和费用 |
| 事实源→缓存/检索→生成 | 用户范围、授权与期限、记录版本、索引代际和向量Space、候选来源 | 缓存和旧索引只提供候选；最终交付前回查当前授权/事实，过期或删除不得因命中缓存重新成为有效证据 |
| 检索→重排→回答验证 | 同查询、同授权候选池、候选ID与原分数、引用版本及完整必要前提 | 评分错配、来源无效、缺前提或支持unknown均保留明确结果；不补写模型漏掉的引用制造成功 |
| 父任务→子任务→汇总 | 父目标版本、预登记子任务/角色、范围、子版本和预期证据集合 | 迟到/旧版本结果拒绝；缺失或矛盾不能因子任务completed而消失，取消等待结束不等于worker已经停止 |
| 运行→归档→评分 | Dataset/Case/Run与配置身份、原输入输出、错误、截断、模型/评分器版本及用量来源 | 记录不完整或版本不匹配不放行；失败保留在分母，未知费用不填零，重放不能回退到真实工具调用 |

交接字段是设计要求，不规定必须采用同一Go结构体。先在独立作品内部实现必要契约；只有多个Lab确实需要相同行为且边界稳定时才提取到labs/internal。公开CLI复用须固定入口、版本、输入输出与运行预算，不能动态执行模型提供的程序或导入其他topic私有实现。[费用Lab的JSON命令协议](../../labs/part3-agent/chapter33/cost-ledger/README.md#固定json命令入口)已提供snapshot/prepare/lookup/begin/unknown/settle，固定合成价格与预算，回应版本、身份、请求与状态须由协调者核对；RunJoint恢复通过lookup核对key/hash对应的原费用ID，同金额错条目不放行。费用命令不继承真实账单或完整作品验收。

推理与恢复作品的执行/费用联合入口按以下契约推进。Checkpoint的RunJoint已接固定动作与合成费用协议，验证八处真实进程退出；动态模型提议、策略比较和完整作品验收仍需扩展：

- **共同身份**：完整Scope/Run、轮次、原ToolCallID及参数/工具版本绑定逻辑调用；物理重试另分配持久尝试身份，再与费用条目关联。账本本地整数ID不能作为全局调用身份。
- **幂等准备**：同一尝试重复准备返回已有费用预留并核对配置；费用侧ReserveAttempt已在Schema2持久绑定key/请求指纹/EntryID，跨重开与并发复用同一条目，旧无映射条目不猜身份。Checkpoint的受控FeeCLI通过公开协议核对程序与回应，RunJoint另保存prepared/received/done/unknown与费用关联，已存返回证据只补费用/结果提交，不重新调用。部分准备成功保留记录，不另建无限预留或猜测退款；模型调用及更完整的任务记录继续按原范围验收。
- **分开提交，按状态恢复**：原结果/错误/usage证据、有效观察与费用结算有明确提交窗口。已有结果但费用未确认时只补核对/结算；费用已知但结果缺失时仍保留执行未知或失败。两文件不冒称共同事务。
- **原始消耗不消失**：批准只读重做建立新尝试，旧已知/未知费用仍占原Run预算；暂停期间不重置配额，保存确认失败时停止新付费接纳。
- **联合故障验收**：在意图、预留、关联、发送、返回证据、观察、结算及最终交接各点退出，核对真实工具次数、Call映射、观察去重、Used/Held和最终目标。固定故障先验证协议，再接真实模型/usage，保留未确认与失败。

该设计对应[Checkpoint的联合恢复讲解](../../content/book/part3-agent/runtime/chapter29-execution.md#执行与费用分开保存时如何对齐)。固定联合样例已经有本地执行证据，但只覆盖单写者、固定只读动作与合成usage；不把它补记为完整推理/恢复作品、真实费用或跨实例验收。

#### 用故障场景检验整条链路

1. **推理与恢复**：分别在工具失败、执行后未提交、提交后未推进和恢复预算不足时中断。核对新实例实际调用次数、已提交结果与最终目标；“恢复函数返回nil”不足以证明任务恢复成功。保留Reflection、Self-Ask和有界搜索对照，结果不因集成难度而改为只测固定计划。
2. **Memory与RAG**：旧查询持有快照时发布新资料，再撤回一份必要证据或使偏好到期。对照缓存/检索命中与最终交付，核对当前事实和完整前提；再分别测HyDE和重排是否改善任务，而不是只改变排序。Vector Store、Redis和SQL联合运行必须有同一次任务的记录，不能拼接各自PASS当成端到端证据。
3. **多Agent**：子任务仍在运行时修订父目标、发生同权威冲突、旧执行者迟到提交，以及竞争者持续提交新任务。核对旧结果拒绝、所有权版本、Missing、共享额度和队列等待；跨实例恢复与持续流量公平性分别验证，有限批次的轮询不替代这些要求。
4. **Eval与可观测性**：加入平均分提高但关键Case退化、工具错误后重试、费用未知和归档不完整的配置。核对门禁、失败分母、逐次尝试与可追溯原记录；模型输出和评分标签分开，语义Judge须有人工校准证据。

每类作品交付一个正常过程、上述关键故障的可复现实验、逐Case报告与架构取舍说明。报告明确哪些行为来自固定控制器、真实模型或存储，解释无收益与失败；架构说明回答新增机制是否改善质量、恢复或效率，以及承担了多少复杂度。额外模型调用、重试和子任务全部计入总消耗，不能只报告成功路径。

建设次序由交接依赖决定：先完善现有Eval集成入口的记录/评分契约，再在推理作品连接执行与恢复、在知识作品连接存储与答案出口，最后完成协作作品的跨实例归属与持续负载。每类作品从首个闭环扩展到上表完整范围，不把首个闭环作为最终验收；四类实现完成后，再按第9、10节核对案例资格、真人迁移任务与发布条件。

### Part 3 的课程边界与参考取舍

Part 3 以“如何把模型能力组织成可控、可验证的执行系统”为主问题。读者完成后，应能解释各部件职责，独立实现关键机制，通过失败实验定位问题，并用评估决定是否需要更复杂的架构。课程对外采用构建篇、运行时、治理篇三大篇，共16个教学单元；Harness是第22单元，承担模型调用、受控执行、状态与验收边界的建立作用。

拆分依据是独立的工程判断与实验目标：ReAct讨论逐步决策，Planning讨论计划管理；Retrieval讨论找资料，RAG讨论资料是否支持回答；多Agent分别讨论委派、依赖调度和后台生命周期。Skills独立成章；工作空间与长期记忆按持久信息管理合章，人工介入与工具接入按受控行动合章，内部保留输入、权限与状态边界。不是每个技术名词都新增一章，Reflection、HyDE、Sandbox等放入对应主题的比较或进阶部分。

| 主线清晰 | 读者能看出本章在整条学习链中的位置，知道先解决什么问题、再连接到哪一层 | 开场是否来自真实工程问题；标题是否围绕一个核心判断展开；与上一层/下一层的交接是否明确 |
| 主题边界明确 | 一页只解决一个主要工程问题，不把相邻职责混成一团 | 是否清楚区分如 Loop/Tool、Session/Context、Retrieval/RAG、Streaming/Serving、Trace/Checkpoint 等相邻概念 |
| 正文与实验强绑定 | 关键论点能回到现有 Lab、测试、图示或记录，不是脱离实现的抽象口号 | 代码摘录、图示、Lab README、测试和正文中的核心判断是否一一对应 |
| 工程证据充分 | 不只展示“成功路径”，还讲清失败、边界、恢复、成本和不能证明什么 | 是否覆盖失败语义、完整性判断、安全边界、排错路径；是否明确 fake/回放/真实模型各自能说明什么 |
| 读者迁移友好 | 前端工程师能把已有经验迁移过来，同时知道哪些类比会失效 | 是否提供前端视角的类比与失效边界；是否帮助读者把页面交互/BFF/API/状态管理映射到服务端执行语义 |

后续章节审查优先围绕这五项记录证据，再决定是否更新 `content_status`。采用与参考课程相似的目录、导航或图示风格，只说明组织形式接近，不说明内容质量已经对齐。

### 贯穿课程的架构视角：从最小闭环理解扩展

从“输入→模型响应→受控动作→观察回填→继续或终止”建立最小决策闭环。学习新机制或框架时，先定位它改变了哪段控制流、管理哪些状态、增加什么执行边界，再判断它解决的问题是否需要这种复杂度。

“在最小循环上扩展能力”是学习入口，不能作为所有架构的强制定义：ReAct改变决策策略，Context改变信息供给，Runtime约束执行，Workflow和调度器可以接管部分控制权。框架可能重组执行结构与状态模型，不能默认每项能力都是保持Loop不变的插件。

以下四个视角组织知识递进，不替代四个Harness子章节组，也不要求按四个阶段机械阅读：

| 理解视角 | 关联机制 | 要建立的判断 |
| --- | --- | --- |
| 建立决策闭环 | Model、Loop、Tool、观察与终止 | 谁提出动作、谁执行、结果如何影响下一轮 |
| 管理信息供给 | Session、Context、Memory、Retrieval、RAG | 保存了什么、本轮看见什么、资料是否支持回答 |
| 扩展决策与协作 | ReAct、Planning、Delegation、DAG、Async Tasks | 是否需要动态选择、计划或分工，控制权和状态如何交接 |
| 约束并验证执行 | Runtime、Recovery、Safety、HITL、Trace、Eval、Cost | 何时拒绝、停止、恢复，怎样证明任务有效且复杂度值得 |

预算、取消、权限和效果对照从最小实验开始；治理专章负责深化与系统整理，不能将约束推迟到课程末尾。

#### 能力扩展怎样沿闭环递进

以“根据当前有效资料回答一个配置问题”为共同任务，先建立能够提议、读取、回填和停止的最小系统，再用实际困难引出扩展。下表规定课程讲解时的承接关系，不要求独立Lab连续修改同一个工程，也不替代章节的真实前置依赖。

| 遇到的问题 | 引出的能力 | 相对最小闭环的变化 | 需要证明的改进 |
| --- | --- | --- | --- |
| 一次读取不足以回答，下一步取决于新观察 | ReAct、Self-Ask | 决策使用新观察，必要时提出可检索的子问题 | 获得必要证据并完成回答，而非只增加推理文字或调用次数 |
| 多步任务有依赖，错误计划需要调整 | Planning、Reflection、有界搜索 | 增加计划、候选和修订状态，由控制器核对后执行 | 同任务、同预算下改善完成度；无收益或失败同样保留 |
| 历史过长，资料会更新或需要跨会话保存 | Session、Context、Memory、Retrieval、RAG | 将保存、选择、召回和答案支持分开管理 | 关键事实与有效来源保持完整；输入缩短或检索命中不能替代回答质量 |
| 一个执行者难以处理不同职责或后台任务 | Delegation、DAG、Async Tasks | 增加角色、依赖、所有权与结果交接；按需使用串行或并行执行 | 与单Agent或串行基线比较质量、协调消耗、取消和恢复行为 |
| 外部能力与指令资源需要统一接入 | MCP、Skills | 增加发现、适配和按需加载，执行许可仍由应用决定 | 接入和加载正确、输入有界，能力使用改善任务且不扩大权限 |
| 执行路径已经明确，动态决策反而增加不确定性 | Workflow、Framework | 程序或框架接管部分控制与状态管理，模型仅负责需要判断的节点 | 固定与动态路径的行为差异可解释，新增依赖和复杂度有依据 |

Coding Agent作为补充阅读使用同一分析方法：定位观察文件、提出修改、应用执行、运行验证与人工介入之间的关系。当前必修主线继续保持只读，不因架构比较引入写文件或Shell执行能力。

运行稳定性贯穿这些扩展。Context管理关注信息损失；工具降级关注失败分类与剩余预算；多Agent关注状态与结果归属；RAG关注资料变化、检索与回答质量的持续评估。每次引入机制，正常路径与关键失败路径一起设计，不能等功能齐全后再补运行边界。

将这条主线落到学习任务时，每组主题都要留下一个可以独立解释的判断：

| 学习阶段 | 需要解释的问题 | 实践产出 |
| --- | --- | --- |
| 建立最小系统：Model、Loop、Tool、Runtime | 谁决定下一步，谁批准并执行，观察怎样回到下一轮，运行为什么停止？ | 一条正常任务与一条失败任务的执行过程，标明消息、调用、状态和终止条件 |
| 管理信息：Session、Context、Memory、Retrieval、RAG | 信息保存在哪里，哪些进入本轮输入，如何确认来源仍有效并支持回答？ | 同任务的资料更新或缺失对照，分别解释召回、输入、引用与任务完成情况 |
| 改变决策：ReAct、Planning、Reflection与搜索 | 为什么需要额外决策步骤，计划何时修订，新增步骤是否值得？ | 与简单基线的逐任务对照，保留失败、全部尝试和预算消耗 |
| 扩展协作：Delegation、DAG、Async Tasks | 谁拥有任务，怎样交接结果，冲突、取消和迟到输出由谁处理？ | 单执行者与协作过程的对照，核对结果归属、共享预算和恢复边界 |
| 接入与治理：MCP、Skills、框架及运行治理 | 外部能力怎样进入系统，哪些控制由应用或框架承担，最终交付怎样验收？ | 接入契约、关键故障及可追溯评估；区分机制正确、任务有效和运行稳定 |

此表用于跨章串联与复盘，具体阅读顺序仍遵循章节依赖。实践产出放在各Lab和作品验收中，不额外建设学习管理平台；对照未完成时保留问题与证据缺口。

#### 构件职责与工程边界

表内机制与应用形态映射到现有26单元，不为每行新增一章。Goal与Error Recovery属于跨章契约，Coding Agent与Workflow用于比较应用形态。

| 构件或机制 | 职责 | 工程边界与课程落点 |
| --- | --- | --- |
| LLM / Model | 理解输入，产生回答或动作提议 | 应用不能因模型生成了意图就直接执行；Model负责响应适配与完整性 |
| State / messages | 保存决策与执行所需信息 | messages只是状态的一部分；预算、进度和待执行调用有独立生命周期，是否持久化由应用决定 |
| Tools | 提供受控的外部能力 | 描述与Schema帮助选择和表达参数，应用执行器仍须校验、授权和限额；Handler不由模型动态创建 |
| Loop | 根据响应与观察推进决策 | 继续与终止有明确分支；模型轮次、工具次数、超时与成本分别约束 |
| Goal / Stop Policy | 定义完成条件及何时停止运行 | Goal、Provider生成停止原因、Runtime终态与业务验收分别判断；end_turn不是任务成功，tool_use不是执行授权 |
| Memory | 保存授权的跨会话信息 | Session保存历史、Context选择输入、Memory管理长期信息；RAG是检索与生成机制，不强制归为记忆的一层 |
| Error Recovery | 在明确条件下修复或恢复 | 参数修复、暂时故障重试、计划修订、执行恢复分别有预算；取消、权限拒绝和结果未知不能盲目重试 |
| ReAct | 交替利用推理、动作与外部观察选择下一步 | 调试记录动作、观察、状态与结果；可见解释不视为完整内部推理，策略效果用任务集验证 |
| Planning | 提出并根据执行反馈修订计划 | 顺序清单、依赖图与动态修订都是选择；DAG与blockedBy不是通用必需接口，调度器验证后才执行 |
| Multi-Agent | 通过角色与任务分工协作 | 串行委派、并行执行与Handoff分别设计；上下文、权限、预算和结果归属明确，Lead与MessageBus不是必需架构 |
| Agent Framework | 复用状态、编排、工具、交接与观测能力 | 先对照已有契约，再判断框架扩展点与语义差异；减少样板不替代架构判断 |
| Coding Agent | 组合代码观察、修改、执行验证与人工介入 | 用作补充阅读；读先于改、编辑匹配校验和验证闭环是实践，具体工具名属于实现选择，不扩展当前只读主线 |
| Workflow / Workflow Agent | 由应用明确约束部分执行路径 | 模型决策与程序编排可以组合；后台任务、Cron和Hook按需选择，不以固定Hook数量定义工作流 |
| MCP | 标准化工具等外部能力的协议交互 | 发现不等于授权；Schema与调用经过本地适配和执行策略；mcp__server__tool可作本地命名约定，不当作协议强制格式 |
| RAG | 为生成提供检索得到的外部证据 | 分别评估召回、输入组装、生成和断言支持；混合检索是策略选择，检索命中不保证回答正确 |

Stop Policy在Model/Loop/Runtime中分别解释响应原因、继续规则和运行终态；任务完成条件在Eval中验证。Recovery在Tool、Runtime、Planning与Checkpoint中分别落地，不重复建设一个含义不明的“通用恢复层”。固定Workflow在Harness、DAG和相关集成实验中比较，Coding Agent不新增必修实现。

角色路由分开核对注册、任务适用范围与执行权限。Delegation实验的SelectRole已提供应用类型映射、允许提议和歧义拒绝，选择后接入现有Dispatcher，不启动模型分类或增加权限。默认契约核对单候选、多候选澄清、未知/不适用角色与坏配置；真实开放任务的分类准确率、澄清效果及角色收益仍按多Agent作品要求验收。

相关一手资料：[ReAct论文](https://arxiv.org/abs/2210.03629)解释推理与动作反馈；[Claude停止原因](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)解释特定Provider的响应原因；[工作流与Agent架构](https://www.anthropic.com/engineering/building-effective-agents)用于比较程序编排与模型动态选择。Provider字段在adapter中映射，课程不以某一家API的枚举定义通用状态机。

#### 每章都要回答的四个问题

1. **问题在哪里**：本章解决最小系统中的哪个具体问题，已有方法为何不足？
2. **机制改变什么**：哪些输入、状态、动作或控制权发生变化，与相邻部件怎样衔接？
3. **代价与边界是什么**：新增哪些失败路径、资源消耗和设计取舍，什么条件下不需要它？
4. **证据如何形成**：怎样分别验证机制正确、任务有效，并判断新增复杂度值得？

这是内容审查问题，不是四个固定模块标题。正文仍按主题知识点自然拆解，用必要代码和图示建立判断；Lab提供正常行为、失败复现和迁移任务。机制实验可以证明执行契约，无法单独证明模型效果；没有真实任务对照时，应明确结论范围。

章节建设按以下步骤落实这些问题：

1. **选定真实困难**：用一个具体任务或失败现象引出主题，明确本章主责及相邻章节负责的问题。
2. **拆解知识依赖**：先讲理解后续机制必需的概念，再解释状态、接口与关键分支；据此命名小节，不按实验函数顺序安排正文。
3. **选择代码和图**：用真实关键片段解释决策与更新，用职责图、时序图或状态图解释文字难以表达的关系；图中名称和边界与实现一致。
4. **设计实践证据**：将完整启动、输出、测试、故障复现和迁移练习放入Lab；正文保留理解机制需要的例子，复杂主题按需增加最佳实践与排障。
5. **收束工程判断**：小结提炼3–5个正文已讲清的要点，并引出下一篇要解决的问题；随后按章节审查表分别核对内容、代码、效果与读者证据。

上述步骤约束作者的工作，不作为读者正文的固定标题。章节形式可以不同，但主题覆盖、来源、原练习和验收范围不能因结构调整而丢失。

#### 将架构视角落实到课程和实验

每个扩展主题都应让读者看清它与最小系统的差异。沿用Model、动作提议、执行器、观察和运行状态等共同概念；需要改变控制流或状态契约时，明确说明原因。共同概念用于串联理解，不要求所有独立Lab共享一套实现，也不要求每章继续修改上一章的项目。

| 扩展主题 | 相对于最小系统需要讲清的变化 | 应形成的学习与实验判断 |
| --- | --- | --- |
| ReAct与Planning | 下一步动作如何选择，计划何时产生、修订或失效 | 同任务下比较逐步决策与先规划；指出增加步骤仍未改善结果的情形 |
| Session、Context与Memory | 历史、当轮输入和跨会话事实由谁管理 | 区分保存与可见，验证信息遗漏、过期和用户隔离；不将历史当恢复游标 |
| Retrieval与RAG | 外部资料如何成为候选、输入与回答依据 | 分别定位检索失败、上下文丢失、生成失败和证据不足；命中与回答支持分别验收 |
| Delegation、DAG与Async Tasks | 执行者、控制权、依赖和结果所有权如何变化 | 与单Agent或串行基线比较，验证交接、冲突、取消和预算；并行本身不算收益 |
| MCP与Skills | 外部能力如何发现、适配或按需加载 | 分开发现、选择与授权，解释资料或指令进入哪里；接入后仍由应用执行边界约束 |
| Workflow与外部框架 | 哪些控制交给程序编排或外部框架，哪些仍由模型决定 | 用同一行为契约比较默认状态、步骤、错误和恢复语义；不将框架API名称当通用机制 |
| Runtime与运行治理 | 谁持有生命周期、预算、权限、恢复与交付责任 | 结合正常与失败路径，说明何时继续、终止或恢复，以及终态能够证明什么 |

复杂主题的对照先固定任务、资料、允许工具与评价标准，再增加本章机制。比较同时保留任务质量、模型轮次、工具次数、延迟、成本和失败；无法直接比较的计数单位或模型配置单独说明。契约验证与效果对照可以是不同实验，但必须分别标明结论，不能把确定性测试通过当作复杂架构更有效的证据。

#### 从架构定位到章节建设

对每个主题，先沿一次任务的执行过程定位变化，再选择代码、图示和实验。以下是跨章覆盖要求，具体知识深度仍以各章蓝图为准；不要求正文逐行照抄此表，也不新增统一应用或必修章节。

| 主题归属 | 要解释的变化位置 | 正文中的讲解依据 | Lab要暴露的关键问题 |
| --- | --- | --- | --- |
| Model、Loop、Tool、Runtime | 输入适配→动作提议→受控执行→观察→下一轮；Runtime管理整个生命周期 | 响应分支、调用关联、执行校验及终止条件；职责图与有分支的调用时序 | 坏响应、未知工具、观察遗漏、重复调用、预算耗尽与取消；结束响应和完成任务分别判断 |
| ReAct、Planning | 决策依据、执行前计划与执行中修订 | 动作/观察记录、计划状态与修订校验；逐步决策和先规划的对照图 | 错计划、无新信息、重复动作、无效修订；更多步骤是否带来任务收益 |
| Session、Context、Memory、Workspace | 保存信息→选择本轮输入→按需补充历史事实或任务产物 | 历史与输入视图、来源及范围校验、卸载和读取；信息流与生命周期图 | 关键事实丢失、过期、跨用户信息、产物变化；输入变短是否损害答案 |
| Retrieval、RAG | 查询→候选资料→证据输入→生成断言→交付检查 | 召回/融合/重排、证据组装与支持判断；索引和回答路径分开画图 | 有近邻却无证据、排名好却答错、伪引用、冲突与误拒答；检索和回答分层评分 |
| MCP、Skills | 外部能力适配与本轮指令/资料供给 | 发现、选择、批准、调用及加载的关键代码；协议时序或加载数据流 | 重名路由、坏响应、断连、未批准加载和输入膨胀；发现或加载不授予权限 |
| Delegation、DAG、Async Tasks | 单一执行者变成任务交接、依赖调度或独立后台生命周期 | 任务/结果契约、就绪条件、状态和版本；拓扑、调度或交互图 | 上下文遗漏、结果冲突、依赖失败、资源竞争、取消和迟到结果；与单Agent或串行基线比较 |
| Checkpoint、Trace、Eval及运行治理 | 执行过程的恢复、观察、验收、交付和资源约束 | 提交窗口、因果关联、评分规则、授权与预算代码；按问题选状态/时序/边界图 | 重复恢复、缺失观测、误判成功、越权、费用未知和断流；各主题只证明自己的契约 |

正文中的架构定位要落到一次具体任务：哪段输入被改变，哪个状态由谁持有，动作在哪一层执行，结果返回给谁。介绍框架时先做这种映射，再讲API；无法映射的新增能力须说明它为何改变了原有控制结构。

**把Loop跑起来之后，课程重点转向把它跑稳。** 每个主题选择与自身最相关的运行约束深入讲解，跨章再核对这些约束的交接：

| 运行问题 | 主要负责章节 | 必须形成的工程判断 |
| --- | --- | --- |
| Context Window不足 | Context；Session、Memory、Workspace提供信息来源 | 选择、裁剪、摘要、卸载各保留什么，遗漏怎样被发现；输入预算与任务效果同时检查 |
| 工具失败与降级 | Tool、Runtime；Planning与Checkpoint处理不同恢复层次 | 参数修复、请求重试、计划调整和执行恢复分别适用何种失败；次数、期限、费用及结果未知如何处理 |
| 多Agent状态一致性 | Delegation、DAG、Async Tasks；持久恢复衔接Checkpoint | 谁拥有任务和结果，版本何时有效，取消与迟到结果怎样收齐；同进程测试与跨实例证据分别说明 |
| RAG质量漂移 | Retrieval、RAG、Eval | 资料、模型、索引或提示变化后，哪些回归案例和指标需要重跑；召回、支持与任务完成度如何回到具体失败 |

同一问题跨章出现时，主责章解释机制，相邻章解释交接契约并链接主责章。比如Tool讲错误结果如何形成，Runtime讲是否重试，Planning讲是否换计划，Checkpoint讲进程中断后如何恢复；不能四章重复一套泛化的“失败后重试”建议。

学习者每个主题按以下步骤推进，具体操作放在Lab中，正文不套用这五个步骤作为标题：

1. **提出问题并预测**：选一个真实困境，画出当前调用链，预测新增机制的位置、正常结果和一个失败分支。
2. **阅读并核对机制**：用正文、关键代码和图示修正预测，说明输入、状态、动作及职责边界；不只记接口名。
3. **运行并改变条件**：从干净环境启动Lab，改变输入或注入故障，核对观察、状态、预算与终止原因。
4. **解释并迁移**：暂时离开正文，用自己的话解释失败原因，再将机制用于一个未给答案的新任务；能够运行示例不等于掌握。
5. **决定是否采用**：根据任务效果和新增代价，给出采用、简化或暂不采用的理由，明确证据覆盖的范围。

AI用于梳理资料、解释陌生代码、生成待验证假设、提出反例和审查遗漏。学习者先给出自己的预测和解释，再请AI质疑；运行结果由实际执行核对，协议与框架行为回到官方资料和锁定版本源码。迁移练习先独立尝试，AI可以给提示或检查思路，不直接填满答案。学习产出是可复现行为与可解释判断，不建设额外的学习记录或自动复盘系统。

### 各章内容蓝图：Reasoning & Planning

以下小节是编写蓝图，允许实施时根据问题调整标题与顺序。每章仍须覆盖现实问题、职责边界、核心机制、设计判断和学习小结；实验命令、固定输出和测试导读留在Lab。表内Lab与证据是建设目标，不能据此标为已实现。

**agent-loop · Agent Loop：推进一次决策。** 已有样章作为质量基线，不重新堆入Tool注册、检索或部署内容。前置：消息角色、Go接口与context。开场：一次回答不能完成需要外部信息的任务。递进：固定工作流与动态决策→模型/工具/运行时分工→会话、运行、轮次→提议与结果关联→观察影响下一轮→完成、失败与预算终止。代码展示状态、响应分支、回填与取消检查；职责图和决策流程图解释边界。最小Loop实验验收关联ID、历史顺序、错误观察和终止行为。小结强调Final不等于任务完成，自然引出Tool执行边界。

**react · ReAct：根据观察选择下一步。** 前置：Loop、Tool、最小Eval。开场：固定工具顺序无法应对资料缺失与查询歧义。递进：动作与观察的反馈关系→观察信息质量→继续搜索/换工具/报告不足→重复动作检测→用完成度与消耗比较固定工作流。代码展示动作选择的结构化记录和失败反馈；时序图比较一次查询与追加查询。实验用相同任务集比较固定策略和ReAct，观察遗漏与额外成本。fake验证机制，真实模型受控评估策略效果；不要求记录或展示模型隐藏思维链。Self-Ask作为查询分解对照，不另扩成一章。

**planning · Planning：管理可调整的任务计划。** 前置：ReAct、Runtime。开场：长任务出现漏步骤、重复执行与目标漂移。递进：按输入、产物和完成条件拆步骤→计划项与真实依赖→计划/执行职责→执行反馈更新计划→独立任务验收→有界反思、分支搜索与后续经验。未知信息下先细化近期动作，不编造远期引用；区分数据依赖、资源限制与展示顺序。代码展示计划状态、更新校验和重规划预算；计划修订图说明完成项、失败项与新增项。实验比较ReAct、Plan-and-Execute及有界反思，检查完成度、无效步骤与成本；错误计划和反馈缺失必须复现。有界算术搜索增加显式稳定操作数配置，旧下标版本与失败保留；标识只在当前候选解释，整批验证后才发布子状态。真实对照已推进中间转换；旧配置缺操作符，完整字段配置仍有已消费标识或深度耗尽，评价保持无区分；参数定位、动作完整性和最终目标分别验收，不继承完整搜索收益。搜索另提供生成后目标验证，默认保留后验证不变；低分完成产物的控制反例可被提前确认，但旧模型记录重放没有收益，验证成本另记。DAG执行器留给调度章，模型生成计划不直接成为受信任的可执行图。

算术搜索对照另设离线可解性参照：三次两两合并、精确分数与完整叶集合验证，枚举额度耗尽保留unknown，完成全部探索才判无解。现有四题中三题可解、一题无解；程序参照不进入模型输入、不增加案例数，也不以不同搜索预算替代真实策略收益对照。正文区分可解性、候选有效性、剪枝与预算失败，具体操作及结果在策略Lab维护。

### 各章内容蓝图：Tool Calling、Agent Runtime / Harness 与 MCP / External Tools

**model · Model：一次推理的输入输出。** 前置：Go接口、JSON、HTTP、错误链与context。开场：Provider返回可读文本，却无法稳定交给程序执行。递进：Token/上下文窗口/采样与能力边界→消息与工具响应→Provider适配→结构化输出与校验→超时、限流和usage。代码展示统一响应类型、HTTP适配关键路径和坏JSON处理；请求响应图区分应用与Provider职责。实验使用fake/httptest验证格式、取消和错误保留；真实Provider仅用于有费用上限的能力对照。Attention、Embedding与KV Cache解释到能判断输入长度、缓存和延迟，完整训练原理不混入接口实现。

**tool · Tool：受控执行模型提议。** 前置：Model、Loop。开场：模型生成一个看似合理的名字和参数，应用仍不能直接执行。递进：工具描述与Schema→注册和能力清单→类型/业务校验→调用与结果契约→稳定错误与有限修复→并发的结果顺序。代码展示Registry、执行器和校验分支；执行流程图标出拒绝边界。实验覆盖未知工具、坏参数不执行、业务失败、取消和输出大小限制。工具召回先做静态清单，再讨论按需发现；MCP负责协议，安全章负责系统威胁模型。

**runtime · Runtime：管理一次运行。** 前置：Loop、Tool、Go并发。开场：单个Loop能完成请求，却无法明确回答运行状态、资源归属和停止原因。递进：Run/Step/Event→合法状态转换→策略与执行分离→独立预算→重试与退避→取消、清理和并发所有权。代码展示状态转换、策略检查与事件提交；状态图说明完成/失败/取消分支。实验验收终态唯一、错误分类、重试上限和资源释放，支持race。持久恢复由Checkpoint负责，网络入口由Serving负责；先确定内存语义，再扩展外部存储。

**session · Session：管理会话历史。** 前置：Model、Runtime。开场：续聊丢失关联、两个用户串话或调用方修改已保存消息。递进：消息关联→会话所有权→不可变快照→追加顺序→续聊与并发冲突→过期与隔离。代码展示快照、存储接口和版本冲突；时序图呈现并发追加的冲突。实验覆盖嵌套复制、用户隔离、过期和并发策略。Session保存对话事实，Context选择模型输入，Checkpoint保存执行进度，Memory保存授权的长期信息。

**checkpoint · Checkpoint：恢复未完成执行。** 前置：Runtime、Session、后端事务与幂等。开场：工具已完成、观察尚未提交时进程退出，重启可能重复执行。递进：恢复所需状态→保存点与提交窗口→领取与并发恢复→幂等/结果未知→版本兼容与恢复策略。代码展示执行游标、结果提交和恢复分支；崩溃窗口时序图解释重复风险。实验在不同窗口注入退出，验证已提交结果不丢、重复恢复可识别；不承诺任意外部工具exactly-once。工具只读，写入仅限Lab自己的恢复状态。

### 各章内容蓝图：Multi-Agent

**delegation · Delegation：委派任务与交接结果。** 前置：单Agent契约、Context、最小Eval。开场：单个Agent承担过多角色，信息与工具互相干扰。递进：执行者、调度与等待方式的选择→角色路由与工具范围→任务/结果契约→共享与隔离上下文→子调用与Handoff→结果冲突与汇总。代码展示任务封装、输出校验和交接约束；拓扑图比较委派与控制权移交。实验比较单Agent和受控委派，覆盖无效结果、权限继承错误和递归委派上限。多个角色不自动提高质量，必须与相同任务、可比消耗的基线比较。

Delegation另有独立SQLLease机制：隔离delegation_lab中的Scope/Task主键、数据库时钟、单调Epoch与owner/epoch/有效期/未提交条件核对。真实父子进程分别领取1/2，在新结果写入前拒绝旧epoch及错误owner，新结果提交后旧进程不能覆盖，已完成行即使到期也不重新领取。到期为测试管理连接受控注入，Owner为应用演示身份；机制未联合文件Handoff快照、原预算、续租或外部工具fencing，不能补记完整跨实例恢复或认证完成。

SQLLease提交另覆盖行锁等待跨越实际租约期限：原UPDATE在未修改行的等待后仍可能接受过期结果，现用MATERIALIZED CTE先取得FOR UPDATE锁，外层再判断owner/epoch/期限/未提交。真实数据库等待状态与服务器到期时间分别观察，修复后迟到提交拒绝且双进程护栏仍通过；结论限于该短SQL提交点，不替代客户端交付、续租或外部执行状态。

SQLLease另连接持久次数预留：同Scope/Task原Limit/Reserved保留，重新prepare不重置或扩大；锁定租约与预算后按有效owner/epoch和余额原子预留。真实父子进程已验证原上限2、旧占用1继承到新epoch后只剩一次；并发两请求竞争一额度仅一个接受。此为保守接纳计数，确认未知不自动退款，尚无稳定尝试ID的幂等预留/发送意图或真实费用；独立Commit仍不强制预算，统一协调入口和完整Handoff/账本交接继续按原范围实施。

**dag · DAG：按依赖调度任务。** 前置：Delegation、Runtime、Go并发与图算法。开场：多个子任务可以并行，但依赖未满足或失败会导致错误汇总。递进：必要输入与业务依赖→任务图与校验→就绪队列与拓扑→并发限额→部分继续/fail-fast与业务部分结果→失败/取消传播→资源竞争、背压与公平→关键路径及完成条件。代码展示循环检测、调度器和结果提交；DAG及状态图说明依赖就绪与终态。实验覆盖环、部分失败、队列满、取消和race，并验证聚合只使用有效结果；迁移练习检查无环但遗漏业务依赖的反例，并自行增加等待与执行时间记录。关键路径算例用于理论判断，不冒称实测加速或现有时间戳功能。规划提出依赖，调度器验证与执行；不让模型文本直接控制并发资源。

**async-tasks · Async Tasks：管理后台子任务。** 前置：Delegation、Runtime；持久化扩展需Checkpoint。开场：长子任务阻塞主Agent，用户无法查询、更新或取消。递进：同步与异步选择→父子任务寿命与结果准入→任务ID及状态独立保存→start/check/update/cancel/list契约→结果收取→竞争与迟到结果→同进程/远程生命周期。代码展示Task Store、版本化更新和取消协作；状态图与交互时序图解释后台运行。实验覆盖重复启动、更新与完成竞争、主会话压缩、取消和任务回收。先实现同进程worker，不把goroutine当作持久任务或无限worker pool。

DAG与有限资源调度共用worker执行边界：入口已取消时不调用Handler，返回后取消优先于输出上限，失败文本不交付；完成事件仍返回调度器收齐并回收资源。running只表示已派发，不能用它证明下游调用已发生。两处取消/收齐与资源回收已按原race实验复验，检查后取消竞争、非协作回调与跨实例执行归属仍保留原边界。

DAG资源调度另有RunReadyStream：有限Run内运行中接纳就绪任务，保留最近派发位置以处理新租户加入；合法等待按初始容量校验，派发才检查空闲资源。关闭输入后收齐，准入失败或取消停止派发并释放在途资源。受控goroutine对照已核对A运行时加入B、B获下一可用轮次、待排/总接纳上限与取消回收；该证据超出预先固定批次，但仍不是无限持续流量、加权/抢占或跨实例公平证明，原多Agent作品要求继续保留。

动态接纳的调用层另有固定-live演示：调度器因队列超限收齐worker后，取消producer生命周期并等待其退出；只由producer关闭输入，发送响应context。原省略取消的反例直到父期限才退出，修复后在父期限前完成，保留ErrQueue、归还资源且不交付迟到结果。该例补调用层退出，不替代远端任务源、持久接纳或非协作抢占。

**safety · Safety：约束可执行能力。** 前置：Tool、MCP、Context；工作空间与多Agent按案例选读。开场：工具资料中的指令诱导模型请求越权动作。递进：资产与信任边界→不可信数据和指令→最小权限与授权→输入/输出与敏感数据→隔离/Sandbox→对抗评估与处置。代码展示应用层策略拒绝和脱敏；信任边界图定位外部资料、模型和执行器。实验覆盖注入、权限扩张、跨用户数据、路径与日志泄漏，验证拒绝发生在执行前。Prompt无法替代权限控制，人工确认也不能扩大系统允许的能力范围。

**cost · Cost：控制每个成功任务的消耗。** 前置：Runtime预算、Eval与usage。开场：换用便宜模型或增加并行后，成功任务总费用反而更高。递进：费用/Token/延迟记录→独立预算与预留→每成功任务成本→缓存和模型路由→降级与质量约束→容量和SLO取舍。代码展示usage ledger、预算预留与结算；质量/成本对照图说明选择。实验固定usage验证预算，再受控比较模型/缓存/并行方案，记录价格版本、延迟和成功率。估算与实际账单分开，失败和重试也计入消耗，不以便宜单次调用代表系统节省。

**hitl · HITL：等待人工决策并继续执行。** 前置：Runtime、Checkpoint、Safety、Serving。开场：任务需要确认时，简单阻塞等待会丢状态，迟到确认又可能批准已变化的请求。递进：审批触发与暂停状态→待审批动作快照→确认/拒绝/修改→版本绑定与恢复→过期、撤销和审计。代码展示Approval Request与恢复校验；状态图解释waiting与终态。实验用只读工具请求模拟审批，覆盖拒绝、重复确认、过期和参数变化后旧确认无效。审批由真实调用方明确操作，不让模型替人批准；权限仍受应用注册表约束。

### 阅读依赖、学习路线与时间预算

先补最小Go前置：接口、错误链、JSON、context、HTTP、测试；并发章再补channel、锁与race，存储章再补事务和幂等。已有后端经验可以按缺口补课，不强制先逐页重读Part 1/2。

- **基础路线（10单元）**：Harness→Model→Tool→Loop→Runtime→Session→Context→Retrieval→RAG→Eval。Eval的最小Case/Scorer在ReAct及其他策略实验之前引入，完整专章可后读。这条路线先形成能解释、能拒绝无效引用、能诊断失败的只读资料助手实验。
- **完整路线**：基础路线后学习Trace、ReAct/Planning、Checkpoint、Memory，再进入Delegation/DAG/Async、MCP/Skills/Workspace，最后系统整理Streaming/Serving/Safety/Cost/HITL。Streaming也可在Runtime后用固定事件源提前体验。实际前置以各章蓝图为准，不要求一次读完一个目录组。章节清单的prerequisites表达必需知识，不把页面前后顺序自动复制成前置链；Streaming不要求Async，Memory不要求Workspace，MCP不要求Trace。语言/并发/SQL前置仍在相关正文与实验准备中核对。
- **专项路线**：Runtime方向深化Checkpoint、DAG、Async、Serving、Trace；知识系统方向深化Context、Memory、Retrieval、RAG、Eval；集成方向深化MCP、Skills、Workspace。权限、费用和错误约束贯穿每条路线，不等到Safety与Cost章才出现。

时间为学习预算估计，不是内容生产工期或完成承诺：基础10单元约50–70小时；其余16单元约100–150小时；Go补齐及存储/并发前置另预留20–40小时。总计约170–260小时，以每周8–12小时约15–33周；每阶段用实际故障解释和迁移任务校准速度。24周全课程目标只能优先覆盖基础与所选方向，不能同时保证所有37单元都达到作品级深度。

每次学习按“先预测一个行为→读对应机制→运行最小实验→修改条件并制造故障→闭卷解释→迁移到新任务”推进。AI可辅助定位实现、提出反例和解释缺口；关键状态、权限与错误处理由学习者核对，并至少独立完成一次关键修改。正文不要变成AI提示词清单，Lab不要预先填满练习答案。

读者完整实践路线在[Harness正文](../../content/book/part3-agent/building/chapter22-architecture.md#从部件理解到完整实践)维护八阶段，覆盖全部26主题；公开导航归属由构建篇、运行时、治理篇表达，推荐阅读与真实知识前置分开。每阶段关联现实问题、核心正文、失败判断和迁移证据；8–12小时是每周机制学习预算，不承诺一阶段一周。固定契约、显式真实效果与真人反馈分别验收，八阶段表不是另一份章节目录或完成状态地图。 Eval在这条路线中分次阅读：第二阶段建立Case/Run、Runner和固定评分；RAG之后回读证据支持与评分校准；Planning之后深入等条件对照与门禁。回读完整覆盖原章，不将首次入门视为完整Eval或作品验收；具体入口随Harness正文维护。

每章交付包包含：主题正文、配套Lab README/元数据/源码及必要测试、需要的可编辑图源与SVG、来源与版本说明、四维真实状态。现有规则和模板是强制约束，不另造平行质量规范。提交前依次检查：

1. **主题成立**：读者能说出本章解决哪个现实问题，哪些相邻职责不在本章；说明输入、状态、动作或控制权发生什么变化。核心小节构成因果或设计递进，避免目录名词堆叠。
2. **机制讲透**：输入、状态、输出、关键分支、失败传播和适用条件都解释到位；核心实现有必要代码，不能只列接口然后让读者自行看Lab。
3. **图文代码一致**：命名、状态和顺序一致；每个图回答一个理解障碍；关键代码保留错误与边界，真实摘录对照源码，教学变体明确说明。

5. **表达与收尾有效**：流程使用有顺序的步骤，关键判断适度加粗，状态与接口用代码格式；小结提炼3–5条具体判断并解释其含义，从本章留下的问题引出已有下一篇。去掉重复声明、空泛评价和实验完成清单；不得将未建设主题链接成可阅读页面。参考文档说明用途并核对出处。
6. **证据分开**：分别验证机制正确、任务有效与复杂度收益，再做内容审校和真实试学；读者能解释失败、完成迁移任务，才有学习有效性的证据。未做试学保持pending，不能由作者或AI自评替代。

基础批次与信息批次各安排一次真实读者试学，重点检查前置缺口、图示理解、代码与概念关联及迁移任务，而非满意度打分。只对本次变更运行规则要求的检查；文档规划执行validate-docs，正文与Lab建设按改动类型执行book、site或完整validate。来源检索日期和后续引用revision写入私有审查记录；实施引入第三方材料时同步公开归属。

## 5. 六个月学习与作品路线

24 周路线按能力依赖组织，不要求一周对应一章，也不要求 Lab 复用上一周的工作区。

已有后端经验、需补Go的读者每周8–12小时：先体验现有Console，再读Model与Loop、Tool，按缺口补JSON、错误、接口、context与HTTP。编号迁移后导论按主题更新入口。每周约2小时问题与阅读、3–4小时运行与修改、2小时故障与测试、1小时闭卷解释，其余时间补基础，以一个可解释机制为单位推进；24周路线是能力组织目标，未填补内容与基础缺口时不能承诺按期学完。

每周完成当前章节和独立 Lab：从干净目录启动，复现正常路径和至少一个失败路径，完成练习，记录指标和一项架构取舍。周次、验收人、修改文件和 CI 矩阵不写进章节正文。

六个月结束时至少应展示：真实模型与工具的受控 E2E、确定性 Runtime、四类作品级 Lab、100 个以上版本化 Eval cases、暂停/取消/恢复/重放、延迟与成本报告、负载与故障实验、Threat Model、SLO、Runbook，以及关键设计的替代方案与适用边界。

| `scripts/prep-book.mjs` | `content/book/chapters.json`、正文、Lab 元数据 | 改写或润色教学内容、联网抓取正文 |
| `src` | 生成 collection、公开元数据、`public` | 成为正文或课程状态的真源 |
| `labs` | 标准库、`labs/go.mod` 依赖、稳定 `labs/internal` | 其他 topic 的私有实现、上一章运行状态 |
| 独立应用 | 自己的 domain、ports 和 adapters | `labs/internal`、模型驱动的领域规则 |

真实编码/重排联合入口可以复用已明确版本、字段、边界与调用前提的本地JSON CLI协议，不导入其他topic私有实现。当前固定应用路径调用neural-retrieval/encoder.py，输入只为授权后文本；caller核对原批次、revision/Space/截断/维度，门禁与超时由联合入口承担。公开协议不是任意脚本路由或新的共享SDK，协议变更需同步调用方与重放。

复杂 Lab 可以包含 Go、Python 和 TypeScript 子目录，但只创建实际需要的层次。单机制 Lab 保持 `README.md + meta.yml + source + tests` 的最小形态；不为目录整齐提前创建 `pkg`、`internal`、`web` 或微服务。

### 正文组织：固定覆盖要求，不固定主体标题

正文按主题核心知识点展开，现实问题说明学习动机，代码与图示解释机制和取舍。Lab负责实验命令、固定输出、测试导读与练习，代码注释承载局部执行说明；复杂主题可以加入最佳实践和常见问题排查。小结提炼主题要点并衔接已有下一篇正文，不用实验完成清单替代学习结论。

参考[Deep Agents课程目录](https://github.com/datawhalechina/deepagents-in-action/tree/main/content)的能力分章方式，吸收[Agent Harness导论](https://github.com/datawhalechina/deepagents-in-action/blob/main/content/ch01-agent-harness.md)、[MCP](https://github.com/datawhalechina/deepagents-in-action/blob/main/content/ch12-mcp.md)与[Streaming](https://github.com/datawhalechina/deepagents-in-action/blob/main/content/ch14-streaming.md)的问题引入、代码递进和图示组织。参考教学方式，不照搬技术栈、绝对判断或固定标题；代码与图示原创，借用第三方内容另行核对许可和署名。

每篇教学正文只固定三个入口/收尾约定：标题下的“配套实验”链接（实验名称指向对应Lab README）；文末“小结”；随后“参考文档”。正文页尾保留有效学习导航。主体小节名称、顺序、数量与篇幅按主题深度适配，不统一叫“真实问题、架构位置、核心机制、最小实现、失败取舍”。

审查内容而非栏目：读者是否知道真实困境、部件在架构中解决什么、输入输出和责任边界、机制为何成立、代码如何实现、结果如何观察、失败如何传播与修复。认知章可以先解释选择与架构，机制章以实现展开，工程章可以从故障复现与逐步修复进入。代码、图示、错误在首次需要判断的位置出现，不集中堆到章末。

开场允许充分分析真实问题，不保留不超过3行的硬限制；不设置“本周任务、修改文件、验收负责人”等项目管理栏目。参考文档说明来源能补充什么，版本化事实回到官方资料或可复现实验。

流程和分点要让读者能据此判断下一步：

1. **识别起点与条件**：说明谁触发、需要哪些输入或状态，避免直接堆接口名。
2. **按执行顺序展开**：有时间顺序的内容用编号步骤，每步写清动作、状态变化与交接对象；互相独立的原则才用无序列表。
3. **就近解释分支**：指出什么条件下继续、拒绝、终止或恢复，不能只写正常路径。关键代码紧随相应机制，不按源码文件顺序铺开。
4. **核对出口**：说明输出或终态能证明什么、仍不能证明什么。存在分支、回路或并发时，配流程、状态或时序图；简单顺序无需重复画图。

加粗突出值得记住的判断，代码格式突出实际字段、状态与接口，避免整段加粗或每句都做强调。源码出处用自然行文链接，例如“执行分支见[Loop实现](../../labs/part3-agent/chapter23/minimal-agent-loop/main.go)”；片段性质在首次出现或确有歧义时说明，不反复插入“这不是完整可运行程序”等注释。删套话不能删掉必要的运行前提、错误语义与适用边界。

小结先用一句话收束本章解决的问题，再列3–5个有解释的要点：**要点名称或核心判断**后说明机制、工程含义或适用条件；避免只有名词、口号或未经正文论证的新结论。最后承接本章尚未解决的相邻问题，说明下一篇将补上什么能力，并指向已存在正文。小结不是测试结果、函数清单或正文标题的重复；正文也不为迎合小结格式统一套标题。

正文取消独立“动手练”栏目，原练习迁入对应Lab README或实验文件；任务、边界、故障和验证不得丢失，不填满答案。Lab保留“预测→运行→故障→解释→迁移”的训练任务，正文仍可就地提示一个值得预测的输入。Go实验不强行包装成Notebook；仅确有交互执行价值的Python对照使用Notebook。

章节规范、模板与AGENTS已经采用主题主线和固定收尾约定；检查器对16个已整合Part 3单元采用新结构，对其余旧正文保留过渡校验。每次新增或迁移篇目，同步适用页面清单、完整性基线与反例，解除该页“踩坑清单/动手练/链接”旧栏目要求，核对顶部实验入口、固定收尾、代码声明、资源与链接。保留篇目完整性与失败测试；目录存在、字数和代码块比例都不能替代内容审校。已人工核对的摘录与图示不等于全书自动验证，Agent当前真实摘录已按关联源码校验，并有改值/改类型/多行字符串反例；教学变体与其他图示源格式仍需各自验证；当前Python/SVG重建一致与静态结构已有专门检查，语义不由此推导。

### 从样章确定的课程建设要求

Agent Loop样章经过主题拆分、正文重组、代码与图示补充、流程提炼和小结改写，形成以下要求。它们适用于Part 3全部主题；样章的具体实现与小节标题只供对应主题参考。

| 样章修改 | 后续章节采用的要求 | 审查时看什么 |
| --- | --- | --- |
| 将Tool Calling与Agent Loop分开讲解 | 按构件职责拆分主题；组合机制归入Harness，相邻部件通过明确接口串联 | 本章能否围绕一个问题深入展开，跨章是否漏掉交接契约 |
| 从现实困境进入，再拆解核心知识点 | 引言交代问题和架构位置；主体顺序服从理解依赖，标题针对本章技术问题 | 去掉Lab链接后，正文是否仍能独立讲清主题 |
| 将实验输出和测试导读移出正文 | 正文解释机制与取舍，Lab README承载启动、输出、故障和练习；局部实现说明留在代码注释 | 是否按函数或测试顺序写成实验说明，原练习是否完整保留 |
| 用关键代码和图示支撑讲解 | 代码呈现真实决策条件与状态变化，图示解释职责、时序、分支或生命周期 | 文、图、代码是否使用同一概念，是否保留影响行为的关键分支 |
| 将密集的流程描述改成步骤和要点 | 有顺序的动作编号展开，独立判断分点表达，关键条件适度加粗 | 读者能否据此判断下一步，以及何时拒绝、终止或恢复 |
| 按复杂程度补最佳实践与排障 | 实践建议有适用条件；排障从现象逐层定位原因，再给修复与复验 | 建议是否解释原因，是否能缩小故障范围，而非泛泛提醒 |
| 重写小结并承接下一章 | 收束问题，提炼有解释的工程判断，再引出尚未解决的相邻问题 | 是否重复函数、测试或标题，后续链接是否对应实际学习依赖 |
| 删除套话和反复的代码性质提醒 | 使用具体、直接的中文；首次说明片段性质与源码出处，后续仅在性质变化或有歧义时补充 | 简洁是否以删掉事实、运行前提或工程边界为代价 |

固定格式仅包括顶部“配套实验”、文末“小结”“参考文档”及有效导航。上述要求规定知识覆盖与表达质量，不把“现实问题、架构位置、核心机制、最佳实践”设为所有章节必须照抄的模块。

### 九类知识组如何适配样章要求

各组沿用相同的质量标准，但选择不同的讲解重点。以下是选材与组织依据，不是各章必须复用的小节标题。

| 知识组 | 问题与知识拆解重点 | 代码和图示重点 | 实验与效果验证重点 |
| --- | --- | --- | --- |

### 逐章质量验收：主题、机制与学习证据

按下面的检查点审查每个教学单元。它们约束内容质量，不规定正文的小节标题。详细写作规则见[章节规范](../rules/book-chapter-contract.md)，编辑起点见[章节模板](../templates/book-chapter.md)，实际审查依据填写[章节审查表](../templates/book-chapter-review.md)；[AGENTS.md](../../AGENTS.md)负责规则入口与执行要求。

| 检查点 | 合格依据 | 需要返工的表现 |
| --- | --- | --- |
| 单一主题与覆盖 | 标题能说明本章问题；核心知识点有讲解、例子与边界；相邻章职责明确 | 合章后未区分相邻职责，或只列术语与接口，把解释推给参考资料 |
| 现实问题与架构位置 | 引言呈现具体困境；读者知道部件承接什么输入、管理什么状态、向谁交付结果 | 空泛介绍技术价值，读完仍不知道为什么需要该部件 |
| 扩展关系与跨章衔接 | 能指出相对最小闭环改变的信息、决策、控制权或运行约束；主责机制深入讲，相邻章交接明确 | 将每个架构作为全新术语重学，默认所有扩展都保持Loop不变，或跨章重复而漏掉状态与结果交接 |
| 知识递进与技术深度 | 按理解依赖展开核心机制，代码、过程例子和图示共同解释关键判断 | 按实验函数或测试名依次解说，以运行结果代替机制讲解 |
| 过程与要点表达 | 有顺序的内容形成步骤，分支写清继续、拒绝与终止条件；关键判断适度加粗 | 一段文字塞入多个动作，或只有高亮口号却没有状态与条件 |
| 代码与图示一致 | 摘录有真实来源；变体说明省略；图中名称、方向与状态符合实现 | 用伪代码冒充实现，配装饰图，或反复插入与学习无关的代码性质提醒 |
| 失败、取舍与排查 | 说明关键失败的触发、传播、恢复与预算；复杂主题按需提供最佳实践和分层排查 | 只有正常路径，或给出不能定位故障层的建议清单 |
| 实验与迁移练习 | 顶部链接独立Lab；README保留原任务、实际起点、修改目标、反例与可执行标准；新验收测试须被实际发现 | 正文变成操作手册、实验依赖上一章、给完整答案，或用原测试/空筛选结果冒充迁移任务通过 |
| 小结与阅读衔接 | 收束本章问题，提炼3–5个有解释的工程判断，并引出已有下一篇解决的相邻问题 | 重复标题、函数或测试结果，或在小结引入未经正文解释的新结论 |
| 来源与结论范围 | 文末参考文档含官方来源；版本、许可与归属可核对；结论匹配实际证据 | 将fake契约测试说成真实模型效果，或把小样本结果推广为普遍优势 |
| 学习效果 | 读者能独立运行、解释关键失败，并将机制迁移到新输入或任务 | 只用篇幅、代码块、截图、页面齐全或自动测试通过证明学会 |

每章交付先检查主题覆盖，再核对实现与图示，随后验证实验，最后回读正文与小结。未讲清关键机制时继续修改内容，不靠新增固定栏目补齐；没有真人试学时，读者状态保持待验证。参考课程是教学质量的对照对象，是否达到相当质量须由这些证据判断，不能仅凭采用相似布局宣称。

### 课程交付的判定顺序

“采用样章写法”和“达到课程质量”分开判断。每个教学单元按下表检查，具体依据记录在章节审查表中；第4节继续维护实现、代码、内容与读者四维状态，不另建一套状态地图。

| 判定 | 必须回答的问题 | 可接受的依据 | 不足时如何处理 |
| --- | --- | --- | --- |
| 主题覆盖 | 第3节蓝图的核心知识点是否讲清？ | 正文位置、关键例子、相邻章交接及未覆盖项的去向 | 补讲解或调整职责，不能只增加标题和参考链接 |
| 机制成立 | 代码和图中描述的行为是否实际发生？ | 源码一致性、正常与关键失败实验、图示语义核对 | 修正实现、图或叙述，并重跑受影响检查 |
| 任务有效 | 接入真实模型或外部能力后能否解决目标任务？ | 版本化任务、完整原始结果、明确评分依据与失败记录 | 保留机制证据，继续处理效果缺口；不得用fake成功替代 |
| 复杂度值得 | 新机制比简单基线带来什么收益和代价？ | 同任务与可比预算下的成功率、步骤、延迟或成本对照 | 如实说明无收益或适用条件，不宣称普遍优势 |
| 读者学会 | 读者能否独立运行、解释失败并迁移？ | 干净环境试学、具体阻塞点与迁移任务结果 | 修正文案、前置路线和实验；无反馈保持待验证 |

知识讲解章不必为了表格新增真实模型实验；是否需要任务效果或复杂度对照，由本章蓝图及其结论决定，不适用须说明理由。四类作品级Lab、累计不少于100个合格Eval案例和至少两个阶段真人试学仍按第9、10节验收，不能由16篇正文齐全替代。

### 质量规则的执行入口

Agent Loop样章确定的是讲解深度与审查标准。后续章节先拆解本主题，再选择适合它的叙事、代码和图示；不得将样章的小节名称、段落句式或实验流程复制成全书模板。

| 约束 | 执行入口 | 交付时核对 |
| --- | --- | --- |
| 主题拆解、现实问题、架构职责与技术深度 | 本方案第3节蓝图及[章节规范](../rules/book-chapter-contract.md) | 关键知识点逐项落到正文；相邻章职责无遗漏、无混淆 |
| 自然标题、代码与图文递进、要点强调、小结衔接 | [章节模板](../templates/book-chapter.md)结合章节规范 | 主体按主题适配；步骤有条件与状态，表达简洁但保留必要边界 |
| 独立实验、命令、结果、故障与迁移练习 | [Lab契约](../rules/topic-contract.md)及对应Lab README | 实验可单独启动；正文不承担逐行导读，原练习任务与边界有去向 |
| 摘录、图示、来源和内容审校 | [章节审查表](../templates/book-chapter-review.md)及本节验收表 | 代码来源与图中关系可核对，结论不超出实际证据 |
| 任务必读、变更纪律与验证命令 | [AGENTS.md](../../AGENTS.md)及[Makefile](../../Makefile) | 按改动执行对应检查；实现、代码、内容和读者状态分别记录 |

每个主题按以下顺序建设和修订：

1. **拆解知识点**：确定一个现实问题，列出核心机制、前置知识与相邻部件边界；对照第3节蓝图及架构定位表，说明本章改变的输入、状态、动作或控制权，并解释未覆盖项的去向。
2. **准备讲解依据**：为关键判断选择必要代码、图示和过程例子，明确实现、教学简化与规划能力；先核对官方来源和行为，再组织正文。
3. **完成正文与实验**：正文解释机制及取舍；Lab承载操作、输出、故障复现和迁移任务。复杂主题按需要加入最佳实践与常见问题排查。
4. **回读内容与表达**：先检查知识点是否讲透，再删套话、重复提醒和机械分点；保留事实、源码出处、错误语义与适用前提。检查小结能否提炼本章判断并自然承接下一篇。
5. **验证并记录范围**：执行适用检查，核对源码摘录、图示与实验行为；分别记录内容审校、模型效果和读者反馈，未验证项保留明确缺口。

修改质量规则时，合并到对应真源并检查本方案、规范、模板和AGENTS是否冲突；只有页面结构或检查范围实际改变时才调整检查器及反例。规则更新本身不能把尚未复核的正文标为合格，也不能降低原定能力与效果验收要求。

规则调整后的交付必须能回答三个问题：

1. **约束落在哪里**：课程范围和完成判据更新本方案，写作规则更新章节规范，编辑提示更新模板，审查问题更新审查表，必读与验证入口更新AGENTS。只修改受到影响的文件，核对相互引用与表述。
2. **哪些内容需要重审**：列出受影响的主题与具体位置，对照核心知识、代码、图示、练习和小结重新检查；不能因规则文件一致就批量提升章节状态。
3. **怎样证明已经落实**：执行与改动相符的检查，记录实际内容修订和行为证据；规则通过、内容审校、任务效果与真人反馈分别判断。长期要求保留在对应真源，一次性审查记录留在私有审查材料中。

### 将章节蓝图落实为可审查的内容

每章动笔或重写前，先把第3节蓝图中的核心知识点对应到讲解依据。下面的对应关系用于编辑与审查，记录在Issue/PR或私有规格中，不成为正文的固定栏目，也不新增公开设计文件。

| 对应关系 | 需要明确的内容 | 缺失时的处理 |
| --- | --- | --- |
| 现实问题→主题 | 一个具体任务或失败现象，以及本章要解决的矛盾 | 收敛主题；多个独立职责分别落到已有部件章 |
| 知识点→自然小节 | 读者需要理解的机制、理解顺序和相邻章交接 | 调整小节与讲解深度；不能仅列术语后交给参考资料 |
| 关键判断→代码 | 实际决策条件、状态变化、错误分支及源码出处 | 补关键实现或标明教学变体；不以接口签名替代机制 |
| 复杂关系→图示 | 图要解释的关系、箭头含义、分支与实现范围 | 先核对语义，再检查完整图的可读性；简单关系用文字即可 |
| 工程边界→实验 | 正常路径、关键失败、可观察结果和迁移任务 | 在独立Lab补验证；命令与测试导读留在README |
| 结论→证据 | 本次验证的是契约、任务效果、复杂度收益还是读者理解 | 明确结论范围，保留失败、未知与尚未验证项 |
| 本章问题→小结与后续 | 3–5个正文已经解释的判断，以及下一篇承接的问题 | 重写小结与衔接，不重复函数清单或引入未论证结论 |

对应关系不要求每个知识点各配一块代码、一张图或一个独立Lab。多个知识点可以共用一个有分支的过程例子；同一证据也只能支持它实际覆盖的判断。正文即使暂时去掉实验链接，仍应能完整解释主题；读者进入Lab后，则应能验证这些解释并改变条件，而不只是照命令得到固定答案。

### 代码：实现推动解释，完整工程留在Lab

| 代码形式 | 适用场景 | 正文需说明 | 验证方式 |
| --- | --- | --- | --- |
| 完整最小程序 | 首次建立一种机制 | 文件、工作目录、依赖、命令与预期结果 | 从正文提取，独立运行核对输出 |
| 真实源码摘录 | 工程较大，只讲关键部位 | 来源文件/函数、必要上下文与调用位置 | 对应源码区域核对，运行相关测试 |
| 教学变体/伪代码 | 暂时省略实现以突出关系 | 省略内容与可运行性，不伪称真实实现 | 可运行变体实际执行；伪代码人工审查 |
| 故意失败例 | 展示错误判断的后果 | 触发、现象、原因、修复和复验 | 副本中验证声明的失败，再核对修复 |

正文展示足以解释核心实现的代码，不只列接口签名后让读者自行翻完整工程；也不整段复制与当前问题无关的框架样板。先提出局部问题，再引入需要的类型或函数，紧随事件或状态变化与原因解释；运行命令和固定输出放在Lab。保留影响行为的错误与边界处理，不为缩短片段删掉关键语义；无机械代码占比或固定代码块数量。

真实摘录计划使用函数/区域定位标记，由检查脚本核对与源码的一致性；完整程序提取到临时目录执行。当前Agent真实摘录以关联Lab/共享包源码核对；指定区域未来可确定性生成，普通正文不可被构建脚本润色。默认测试使用固定模型、资料与时间；真实模型效果另用受控E2E和数据集评估。未来检查能力逐项实现，不能因当前部分片段验证通过就宣称全书已验证。

### 图示：按关系选图，与代码共用命名

| 理解障碍 | 图示形式 | 典型用途 |
| --- | --- | --- |
| 部件、职责与信任边界 | 架构图 | Model、Loop、Tool Executor分别负责什么 |
| 一次调用的时间顺序 | 时序图 | 提议、执行、回填、再次推理 |
| 条件分支与处理步骤 | 流程图 | 校验、拒绝、执行、错误返回 |
| 合法的状态转换 | 状态图 | running、completed、failed、cancelled |
| 信息如何被转换和传递 | 数据流图 | 资料、检索结果、上下文、回答 |

一两句话已能解释的关系不画图；复杂部件在首次出现时给简洁定位图，顺序与恢复问题用相应图继续展开。不能把架构、时序、状态和所有实现细节挤到一个全景图，也不要求每章固定配图数量。

图名、部件名和状态名与代码/正文一致；箭头标明调用、数据或事件，配必要图例；已实现和规划能力用明确标注区分。每张图有替代文字，附近解释它支持的判断，图片不可见时正文仍可理解。截图只能证明某个观察，不能代替机制图。

图示采用可编辑源文件与静态SVG成对管理，资源集中在 `public/diagrams/`，普通Markdown与Astro使用同一SVG。当前采用Python标准库生成器，24个源文件及50个SVG在 `public/diagrams/sources.json` 登记，SVG由Part 3正文或配套Lab引用。Agent Loop图由 `public/diagrams/agent-loop.py` 生成，执行 `python3 public/diagrams/agent-loop.py` 可重建。

`validate-book`逐源在临时副本重建并逐字比较，核对登记集合、替代文字、局部引用及受限元素/属性；反例覆盖缺源、额外/重复产物、过期图、脚本、外链、xml:base与缺替代文字。自动检查证明产物可重建及符合当前静态结构约束，图与源码的语义、完整图的布局和读者理解仍须分别核对；临时副本也不是未知生成器的进程沙箱。

后续按图的表达需要选择源格式。Mermaid可用于简单架构、流程、时序和状态图，但引入前须明确工具版本、字体、渲染命令、登记及反例契约，不能只提交SVG绕过真源检查。现有Python/SVG满足需要时继续使用；通用Mermaid渲染器是可选改进，不是课程内容完成的前置条件。

### 首批样章的具体展开

| 样章 | 问题与自然递进 | 核心代码 | 图示与实验 |
| --- | --- | --- | --- |
| Agent Loop | 一次响应为什么不够→如何继续→观察如何回填→何时停止 | 响应分支、loop、历史关联、独立终止条件 | 循环时序；正常完成、不收敛、取消 |
| Tool | 提议如何变成调用→参数契约→注册与执行→错误如何返回 | Tool定义、Schema、注册表、执行器与错误类型 | 执行边界；未知工具、坏参数、业务失败 |
| Streaming | 为什么只有转圈→展示哪些事件→如何传输→断流与停止 | Event、channel、SSE与局部连接回调 | 事件时序；部分输出、断流、迟到事件 |

这张表约束各章的教学主线，不直接复制成统一模块标题。三篇用于校准后续章节的讲解深度和表达方式：读者应能从正文理解关键实现，从顶部实验入口独立运行，并解释正常与失败结果。其他主题已按这套标准建设基础正文，后续继续逐章复核；真人试学单独验收，不能因扩写完成而补记通过。

### 站点阅读体验

保留根目录Astro工程及book单一真源，不创建平行课程站点。目标首页按Go、后端及Agent能力分组，Agent导航按构建篇、运行时、治理篇展示正文；Harness作为普通编号单元给出架构总览，部件页的前后导航遵循阅读依赖而非迁移标识。首页给出阅读路线、章节简介与实验入口；章节页采用课程导航、中央正文、本页目录，移动端折叠导航和目录。

实验链接位于正文顶部，站点可用卡片增强但不能制造重复内容；适用版本和前置知识就近说明。增加代码复制、图示放大、输出与提示样式、主题切换、前后导航和关联实验。未实施章节不进入可阅读导航，缺视频/PDF时不放占位入口；搜索与多媒体后续按需要增加。

现有首页、代码高亮、本页目录、主题与Lab卡片已经存在。章节页已接入课程导航：Part 3按构建篇、运行时、治理篇分组；当前页高亮并展开所属类别，桌面宽屏显示左侧课程、中间正文与右侧本页目录，小屏以原生折叠入口呈现。分组来自 `navigationPath`，页面ID、URL与线性阅读顺序保持稳定；未发布页面不进入导航。生成页面检查逐页核对全部入口、当前页和类别展开，清单检查核对分组归属。首页也按相同清单展示三大篇，提供Agent课程直达入口；所有已发布章节各出现一次，标题层级随分组递进。37单元元数据映射与展示编号已接入。章节代码块已提供复制按钮与可读完成/失败状态，保留原文空白；本站SVG可通过键盘或点击打开原尺寸新页面，已有链接与外部图片不重写。功能只在呈现层增强，不改正文；无脚本时原代码与图片仍可阅读。复制权限受浏览器能力约束，拒绝时提供手动选择路径。当前预览的Clipboard工具读回为空，不能把API完成反馈写成系统剪贴板逐字验收；默认行为测试另行验证复制文本与失败分支。正文监听与开发子进程监督已接入，具体运行边界见下节。content/book/chapters.json管理规划与发布页面元数据，完成度继续在第4节维护。

### 本地启动、调试与生产预览

代码高亮保留源码行与缩进，不自动将长行折成外观上的新语句。窄屏时长代码在代码框内横向滚动，页面本身不被撑宽；复制仍使用原始文本。表格可在自身区域滚动，图示保留原尺寸入口。阅读验收同时核对窄屏与桌面显示、源码行结构和复制反馈，浏览器预览不能替代真人完成实验的证据。

```bash
npm ci
npm run dev -- --host 127.0.0.1
# 浏览器访问 http://localhost:4321/the-way-to-ai-engineer/

# 生产构建和本机预览；端口以命令输出为准。

```

Node版本遵守package.json，Go版本遵守labs/go.mod，锁文件准备依赖后默认验证离线运行。npm run dev由Node监督程序启动：先生成并跟踪content/book正文/chapters.json及labs元数据，再启动受监督Astro子进程。当前采用250ms文件元信息扫描与120ms去抖，避开本机原生监听EMFILE；Vite同样使用轮询。目录外符号链接与生成目录不扫描，只有相关源变化才重建。所有正文先验证/渲染，再逐文件原子替换变化产物，删除撤销页面；未变文件保留时间戳。语法、清单或断链错误可见并保留上一版有效产物，不能把旧页面当作本次保存成功。Lab元数据字段当前未直接呈现，变化触发重新检查章节清单/引用，不制造无意义内容hash。

监督程序转发SIGINT/SIGTERM、关闭扫描与去抖，给自己的子进程最多5秒退出后再强制结束；禁止background/ignore-lock，端口占用报错而非静默开第二个课程服务。锁定Astro在代理环境可能自动后台化，监督程序使用已核对的子进程环境标记保持受控生命周期；升级CLI必须重新验证。真实临时工程已验证源修改进入HTTP页面、非法清单保留旧页、撤销404与恢复200，以及退出清理。文件元信息轮询不保证检测故意保留inode/mtime/size的内容改写，也不是生产文件事务；此时手动content:prepare检查。

## 8. Agent 架构和安全边界

Agent Runtime 的核心模型为 `Run → Step → Event`，围绕 Session、Model、Tool Registry、Tool Executor、Memory、Retriever、Scheduler、Checkpoint 和 Trace 组织。Provider、数据库、工具和框架 SDK 位于 adapter 之后，业务规则不由模型输出直接决定。

关键边界：

| 边界 | 风险 | 强制控制 |
| --- | --- | --- |
| 客户端 → API | 非法输入、越权 | schema、身份与资源所有权、限流 |
| Runtime → Model | prompt 泄漏、费用、不可控输出 | 最小上下文、预算、超时、结构化校验 |
| Agent → Tool | 注入、未知工具、坏参数、副作用 | 注册白名单、参数 schema、审批、审计 |
| Memory/RAG → 用户 | 跨用户泄漏、过期或错误事实 | tenant 隔离、授权、来源、时间和删除策略 |
| Worker → Queue/DB | 重复执行、丢失和提交结果不确定 | 幂等键、lease、checkpoint、outbox |
| 服务 → Provider | 凭据泄漏、SSRF、超时 | 服务端秘密、host allowlist、响应上限、熔断 |

默认 Agent 只读。未知工具、非法参数、超出轮次/Token/费用、跨用户 Memory、引用不可验证或输出 schema 失败时，不得执行持久化或外部写操作。客户端检查只改善体验，最终授权和参数校验必须在服务端。

真实 Provider E2E 只有在显式开关、服务端凭据、host allowlist 和调用预算齐备时运行；默认 CI 使用 fake 和固定数据。日志和 Trace 记录模型、prompt 版本、工具名、参数摘要、状态和耗时，不记录秘密、完整敏感输入或不受控模型内容。

可选 GoTrip 案例仅生成带来源和查询时间的旅行建议。天气、POI、路线等工具由应用显式注册，输出通过 schema 和事实约束后才能由用户主动保存；不注册交易工具。

## 9. Eval、性能与作品证据

联合RAG显式v3将输入引用键投影为evidence_id并保留实际messages，原Go提交摘要与模型消息分开核对。三项原开发任务仍未通过：前提引用缺失、引用结构错误与无依据数值分别保留；不修补原文/输出，不新增独立任务或继承语义Judge已校准。

多来源推导按“断言—引用集合”检查联合支持，单条引用另查归属与贡献，任务完成度另查所有用户要求。三种评分单位分别登记，不能将联合supported复制为每条引用独立supported，也不能要求每条资料单独证明组合结论。缺少前提、明确矛盾与判断未知按冻结Rubric分类；RAG正文说明推导步骤，Eval正文说明计数与校准边界。现有单引用标签统计不自动代表联合语义评分器已完成。

Eval 数据集至少分为 `development`、`regression`、`adversarial` 和 `production-like`，固定输入、期望、评分器和版本。课程完成时累计不少于 100 个案例。

案例累计按任务与环境定义登记，不按提示版本、模型配置、运行次数或单元测试函数累计。跨Lab保留数据集/Case身份、任务家族、来源及版本、当前划分、评分依据与关联Run；旧任务变体和重复运行分别记录。契约、模型任务与Judge校准样本分开报告，案例数量不能证明模型质量或独立泛化。

Eval的[公开登记](../../labs/part3-agent/chapter33/eval-harness/case-registry.json)及[只读核对入口](../../labs/part3-agent/chapter33/eval-harness/case_registry.py)固定所选原文件的字节、版本、读取布局和案例ID，拒绝漂移、重复身份与越界来源。来源声明的split单独报告；Schema2将三组策略及一组Skills共24条定义的当前用途记为regression，绑定公开原记录的哈希与完整Case集合，其余77条用途仍为review_pending。资格全部保持review_pending，合格模型案例数为null。退出0只证明来源一致，不能代替独立性、用途历史或评分依据的审查；登记不依赖私有规格、不增加案例数，也不改写原定义。

当前已盘点的18份JSON定义含101条条目：84条模型输入型任务、14条框架契约与3条评分夹具。新增12份资源核算开发定义区分预留/实耗、重试累计、未知费用/Tokenizer、共享账本去重、容量及假设关键路径；程序参照验证关系与单位，严格输出检查区分known/null/0与引用范围，仅报告numeric_contract_passed；核算模型已实际运行12题，协议可解析1/12、数值合同0/12，均未截断；原文与Token用量保留，不修复通过。独立校准仍待完成。定义超过100不表示100合格案例完成。新增运行诊断家族8份development合成任务覆盖接纳、角色版本、观察遗漏、父目标、提交窗口、撤销、冲突及取消收齐；输入与预期判断分开；新增回答检查分别判断动作、事件覆盖与评分侧原因支持，缺判断保留review，旧输入/答案/量规判定拒绝。已用锁定本地模型实际运行8题：建议匹配6/8、必要引用2/8，原因判断均未知，review2/failed6/passed0；原文/实际输入/截断/用量保留。独立校准仍待完成；已提供不显示机器评分/隐藏标签的原文审阅材料及unknown绑定模板，评审者/参照/理由为空，不计校准通过；另有不读取模型答案的必要证据审阅起点，允许记录整套替代路径，原引用参照仍待独立复核。这里只表示所选文件的定义数量，未证明它们都是不同任务、已校准或独立验收样本；源码内夹具及未登记来源不在此计数中。新增四题在推理前冻结，覆盖三跳别名、字段/单位、条件策略和同权威冲突；首次对照已保留动态/固定方法的所有结果。它们仍属于同一合成资料环境，未成为已校准的独立领域基准。算术搜索、追问、策略、RAG、Skills与压缩仍集中于少数合成任务家族，production-like覆盖和跨Lab资格核对尚未完成，100案例目标继续保留缺口。后续先核对重复、用途变化与评分有效性，再按缺失任务类型补案例，不以批量改名或更换数字凑数。

已登记定义的质量核对：18文件的记录哈希、版本与条目数一致，文件内Case ID无重复；101份完整载荷在仅去除本案例ID/划分/家族后各不相同。该比较保留环境与评分内容，只说明未发现完全同载荷，不证明语义独立、评分可靠或泛化；同问不同失败环境也不能直接判为重复。

| 核对项 | 当前结果 | 后续处理 |
| --- | --- | --- |
| 定义完整性 | 101条与登记数量一致，无所选文件哈希/版本漂移 | 来源或标签修改时保留版本与原记录，不能为修复统计覆盖旧输入 |
| 声明划分 | development 39、regression 6、holdout 6、未明确50 | 先按实际使用记录核对用途；文件名不替代划分，holdout不自动转换为独立验收 |
| 重复风险 | 无完全同载荷组；两组问句重复主要来自契约/评分夹具 | 继续按任务家族、资料环境与约束做语义去重，运行记录/模板变化不计新案例 |
| 合格案例资格 | 完全相异载荷不等于已校准或独立案例 | 资格需明确评分依据、当前用途与运行证据；无依据保持待核对，不用101补记100合格已完成 |

优先补划分与评分证据，再按缺失任务家族增加案例：多来源条件/单位与版本、权限/删除、运行恢复与并发交接、持续负载和成本。未声明或用途已改变的样本可继续做开发诊断或回归，发布验收则需要明确登记的独立集合；采用保守用途不能反过来声称已经证明它的历史划分。

核心指标：

- Task Completion Rate；
- Tool Selection Accuracy 与 Argument Validity Rate；
- Recovery Rate、平均步骤数和人工介入率；
- RAG Recall、重排增益和 Citation Validity；
- Handoff 成功率、循环/死锁/超时率；
- P50/P95 延迟、Token 和每个成功任务的成本；
- Queue wait、Worker 利用率、恢复时间和错误预算。

指标必须能回到 Trace 和具体失败案例。模型输出波动不能被当作随机噪声忽略；开发集用于迭代，回归集用于门禁，对抗集验证权限和注入，production-like 集用于容量与成本判断。

RAG必要前提另外按已复核的证据组检查候选与实际输入。Eval的ScoreEvidenceCoverage已实现独立标注/版本、组内替代、全部组覆盖、Known旗标、缺失Run与未标注分母的集合契约；公开Schema1本地JSON入口可独立生成有界报告，退出0不作为质量门禁。TaskInput与原JSON定义不变。当前标注针对固定合成任务，尚需更广任务的必要组、替代依据、当前授权与实际请求记录，不能由覆盖率推导断言支持或100合格案例完成。

已有原三项联合生成任务的独立真实输入捕获：Go提交载荷摘要与公开合成输入投影核对，旧输出记录不回填；同配置生成仍0/3。覆盖入口确认InputObserved3/InputComplete1，候选未观测，因为此次没有检索。新记录只加强输入与失败的联结，不增加独立任务数；当前组标注仍由作者针对固定案例定义，通用语义与人工校准继续验收。

每个作品级 Lab 需要 README、架构图或文字边界、运行命令、固定测试/Eval、至少一个故障实验、指标结果和已知限制。课程仓库、公开技术文章、架构决策和真实开源贡献可以构成岗位加分证据，但不得把本地测试描述成生产经历。

## 12. 方案维护

以下变化必须同步本文档：产品范围、正式章节、课程路线、目录/module 边界、单一真源、发布架构、Agent 权限、完成定义或长期能力目标。专项写作、Lab 元数据、安全变量和日常命令分别留在对应 rules、templates、源码和 AGENTS，不在本文复制第二份实现细节。

进度、临时排查、一次性迁移步骤和验收输出写入 Issue/PR 或私有 `.specs`，不追加到长期方案。新设计内容应合并进合适章节并删除失效表述，不通过继续拆分设计文件来记录历史。

### 内容目录收敛

课程和面试正文分别迁入content/book与content/interview，labs保持根目录与原Go模块。网站源码src只负责呈现；课程中间副本迁至.generated/chapters并忽略提交。迁移同步引用、监听、CI与检查器，稳定页面ID、网站URL和跳转保持；首题只调整必要图片路径并核对导出一致，远端公众号草稿不操作。历史冻结评测载荷保留原字节，legacySources继续解析其原路径。

### 两个阅读站点的构建与共享托管

课程继续使用astro.config.mjs、src/pages与dist。面试使用astro.interview.config.mjs、src/interview-site与dist-interview，website.json独立声明可见正文。二者复用Node依赖和公共静态素材，导航、首页、内容集合、生成目录及缓存隔离。npm run check:sites检查两个站点，再组装.pages-dist；现有Pages工作流只上传此合并包，课程根路径与全部旧跳转保持，面试位于/the-way-to-ai-engineer/interview/。它们共享域名和一次部署，不能分别设置Pages域名；未提交、未推送时不能声称已线上可用。详见面试专项方案。
