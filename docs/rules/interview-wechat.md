# Agent 每日一题｜合集文章风格与交稿规范

> 适用项目：本仓库的微信公众号「Agent 每日一题」合集。
> 依据：用户多轮确认的要求，以及 Reasoning&Planning 01/03、Tool Calling 01 与 Context&Memory 01 的实际编辑和回读实践。不是从早期被否决的面试式修改方案提炼，也不把单篇历史例外当成后续默认。
> 优先级：本次明确要求 > 已确认的合集规范 > 通用模板。写作、排版与视觉为推荐默认；真实性、授权、保护现稿和真实保存验收不可省略。题目与正文按[面试内容规范](interview-content-contract.md)维护，公众号状态以私有登记与平台实时回读为准。

## 1. 合集组织与标题

合集统一为 **Agent 每日一题**，下设大章节，每章包含多个小 topic。当前用户提出的章节体系：

- **Reasoning&Planning**：推理与规划；已确认标题采用无空格的 `Reasoning&Planning`。
- **Tool Calling**：工具调用。
- **Context&Memory**：上下文与记忆；首篇已采用 `Context&Memory 01`，后续保持同一显示拼写。
- **RAG**：检索增强生成。

推荐标题结构：**Agent 每日一题｜章节名 两位章内序号：questions.json中的title**。`title`是本期主题，`order`主导制作，前置依赖只用于准备资料。历史四篇沿用既有章名、编号和标题；新稿不另造主题标题，同章编号从已占用编号递增并锁定，不随列表重排。题目要改先明确修改题单，不仅修改频道标题。

已确认实例：

- **Agent 每日一题｜Reasoning&Planning 01：ReAct 和 Plan-and-Execute，到底怎么选？**
- **Agent 每日一题｜Tool Calling 01：Function Calling 与 MCP 是什么关系？**

标题不再展示合集总序号 `001/002`，也不在尾部加 `（Tool Calling，1/10）`。序号在每章内递增；尚未确定章内题目总数时，不写 `/10`。旧目录 `agent-daily-001/002` 只用于已有资产定位，**无需重命名或当成新标题总编号**。后续目录选择一个稳定、清晰的 topic slug，章内顺序由稿件元信息维护。

具体主题要能从标题直接识别，不堆括号、营销词、长副标。全文、头图、横封、方形分享图的章节拼写与编号须同步；改题时逐项核对，而非只改在线文档标题。

## 2. 定位与叙事主线

**知识科普为主，面试场景贴合为辅。** 给对 Agent 有基本兴趣的技术读者讲明白机制、职责和实现边界；不是背答案、面试追问清单或练习册。

整体主线：**案例引入 → 概念与机制 → 适用场景／工程边界 → 案例小结，正面回答开头的问题。**

- **案例引入**：具体任务、目标交付物及会遇到的障碍。设计类主题从开发者视角交代已接入的工具、输出约束和验收，再提出模型与程序如何分工；不写成用户向现成Agent交办任务的使用教程。假设案例明确当作教学情境，不伪造亲历故事或实验结果。开头用一句自然过渡引出技术话题，完整的选型结论留到回案例章节。
- **概念与机制**：先解释是什么、解决哪一层问题，再讲如何工作。术语第一次出现时给全称或简短释义；区分模型、宿主应用、工具／服务端等责任主体。
- **场景与边界**：产品／业务场景回答“什么时候有用”；实现要点回答“怎么做、容易错在哪里”。不要互换两列含义。
- **回案例**：用明确、简短的判断回应原问题。按案例中的缺失、超时、冲突等逐项闭合，不重讲所有概念，不强行固定为同一种故障组合。

这条主线是作者的组织依据，不要求文章每段露出“第1步定义、第2步例子”等模板提示。章节数量、段数、字数不固定；一篇聚焦一个可回答的小问题，不膨胀成完整安装教程或泛知识百科。

## 3. 技术章节的统一表达

每个主要技术章节按理解需要组织，不强制拆成三段；概念型文章可将“是什么、长什么样、在模型调用中的位置”集中在概念章，Context/Memory等非主线内容用紧凑对照表辅助。作者明确删去的案例章或配图不因套模板恢复。可选语义如下：

1. **技术讲解**：先用通俗、准确的话解释机制，指出输入、输出与控制权；术语服务解释，不以检索摘要和术语密度代替专业度。
2. **案例带入**：围绕同一案例推进方案，每节只增加一个新问题或条件。例如资料齐全时先比较，漏项或独立核验需要引出拆分，读后才发现的信息缺口再引出受控补查；这是递进方法，不是所有主题必须采用的三阶段架构。
3. **衔接下一节**：说明当前方案能处理什么、仍有什么条件未满足，让下一节解决这个新问题；不重复开头、不用空泛口号过渡。

多方案比较默认用同一案例串联，产品例子只在确有信息增量时补充；单概念文章可用权威产品或技术方案说明应用。产品行为、官方示例和本文工程建议须分开，不推断未公开架构，不为凑品牌或配图数量举例。章节内部可以用自然段、短列表、图或代码，不强制出现“概念／流程与实现／案例应用”三级标题。跨层概念说明如何组合，同层方案比较条件与代价，不能写成互斥的成熟度阶梯。

流程文字优先“**动作或阶段名称：**谁做什么、得到什么、交给谁”的短条目。步数由实际流程决定；协议步骤、SDK封装与应用逻辑须分清，不能把模型声明适配或自定义授权器写成协议强制流程。

版本会影响机制时，说明**本文示例采用的版本／适用条件**并引用对应来源；不要混用 `latest` 文档与历史版本代码，也不要把某一版的握手、字段名或调用方式固化为所有版本的标准。

## 4. 精炼、强调与去 AI 味

- 自然叙述，段落有推进；删除重复定义、空泛过渡、机械口号、面试口述和固定互动结尾，不把成稿拆成满篇提纲。
- **记忆点沿用正文原词**。小结“特性”栏先给加粗短句，再按需补机制解释；不另造一套术语造成前后割裂。
- **核心句同字号强调**：核心章节按需要提炼一句可复用、带必要条件的判断，先用正文解释支撑，再用青绿#2D6A5B和600字重突出，**不加底色**。不加“highlight记忆点”标签、独立口号栏或重复收尾，不放大字号、整段高亮或满篇加粗；检查强调文字及祖先元素都无底色。列表和表格只强调有信息量的引导词，解释保持普通字重。
- 不要求每段有金句，不固定“核心是”“一句话总结”“首先其次最后”等句式，也不禁用合理的有序列表。
- 否定、条件和不确定性不能为精炼被删：未知不等于不支持，步骤完成不等于任务验收通过；“可”“往往”“取决于实现”有含义时应保留。
- 去 AI 味按本地 humanizer 的“标记模式化表达→整体改写→核对事实和衔接→成稿”进行；它是编辑方法，不是AI检测分数。保留条件、来源、否定边界和作者语气，不虚构亲历、数据或权威观点。若该技能不可用，说明实际执行的方法，不谎称调用。
- 评估段先说要判断哪项改进是否值得，再分点交代比较条件、产物质量、失败表现、时间与费用；这些维度按本题增删，不把结构化列点当成已完成实验。
- 每节的概念、流程图、代码、例子、小结使用同一责任划分、术语、完成条件与信息口径。

## 5. 小结表格

比较或归纳内容优先使用 **“小结”标题 + 一句关系说明 + 原生表格**。回到案例的结尾可保持独立章节。

推荐比较列：**对象（模式／技术／组件）｜特性｜适用场景｜工程边界**。归纳知识点时采用 **知识点｜核心结论** 两列；概念辨析可用 **概念｜应用｜技术**。按实际关系选列，不固定配额。首列按真实类别命名：ReAct 与 Plan-and-Execute 可称“模式”，Function Calling 与 MCP 称“技术”；不要为了套表把不同层次的概念写成互斥选项。

- **特性**：加粗可记忆的精练句，复用正文说法；解释不制造新概念。
- **适用场景**：具体产品或业务任务。产品举例以官方资料可观察的工作方式为准，不鉴定其未公开内部架构。无合适产品证据时，用清楚标明的业务情境，不为凑例子编事实。
- **工程边界**：参数校验、权限、路由、反馈、预算、异常、验收、持久化等实现要点或坑；只选与本篇机制有关的点，不把运行时保障说成模式天然保证。
- 表格保持紧凑，能在单元格读懂；不把正文整段复制进去。长内容可删重复解释、拆表或改布局，但不能未经授权删除真实限制。

列宽按内容设计，不固定 15/22/30/33 或 18/22/27/33。公众号可能移除 `colgroup` 或规范化为等宽，必须看实际保存后的布局；属性存在不等于像素比例保留。四列表是这两篇的模式，不是所有 topic 的配额。

## 6. 字体与排版推荐默认

系统无衬线：苹方／微软雅黑，配系统回退；不要求读者安装字体。平台外层文章大标题遵循后台原生样式，正文标题按语义逐级使用、不跳级。

- **普通正文**：15px，400，#333333；行高28.5px，字距0.2px；左对齐，无首行缩进，段后14px。
- **H1**：20px，600，#1F2329；行高30px，段前32px／段后14px。
- **H2**：18px，600；行高27px，段前28px／段后12px；默认深灰。
- **H3**：16px，600，#333333；行高25.6px，段前22px／段后10px。
- **技术主题标题强调**：少量使用青绿#2D6A5B，同级其他标题深灰。颜色表达角色，不按固定标题名字或固定层级套用：001技术节为H2，002技术节为H1。
- **表格**：14px，行高23.8px；左对齐、顶部对齐，单元格内边距8px，1px #D0D7DE细边，表头#F5F6F7。
- **图注／代码说明**：13px，灰色#777777，行高23.4px；图注居中，必要代码说明左对齐。代码边界优先由简短注释承载，不恢复作者已删除的冗长说明。
- **参考资料**：14px，#667085，行高25.2px；左对齐、零字距，完整长URL允许折行。
- **Python代码**：公众号原生14px等宽，约26px行高，多色高亮；长行横向滚动，不缩成小字硬塞。行内code约14px等宽。
- **分隔线**：细浅灰#E5E7EB；控制视觉噪声，避免每段一条线。

15px是本合集已确认的正文默认，12px不作为普通正文。以上不是微信公众号官方统一标准；最终以实际读者渲染可读性验收，可按内容需要调整。

## 7. 头图、封面与正文配图

当前系列视觉锚点：**米白纸艺、克制留白、绿橙角色与具体任务隐喻**。头图要生动贴题、有公众号品味，不是大字报、面试海报、营销贴纸或假微信UI。

- **正文头图**：文章顶部，保留完整主题叙事；合集名、章节名与章内序号清楚，主题词精简。圆角／边距按版面需要，不硬套同一像素值。
- **横版封面**：建议同母版适配2.35:1，主要主题和主体在裁切后仍可识别；不能仅凭本地源图完整就宣布卡片文字完整。
- **方形分享图**：1:1，优先清楚的主体与短章节标识，避开半截英文长标题；允许取母版局部、不包含所有人物。没有合适裁切时，做独立同主题方图。
- **三处一致**：统一主题、系列语言、章名与编号，不要求像素完全相同。正文头图与封面是独立资产。
- **技术／案例图**：精确机制、箭头、分支和角色用确定性图形表达；图片承担教学关系而不是重复正文卡片。每张图与对应标题、图注、源码语义逐项配对。
- **图注**：默认“图n：简短图片标题或功能”，不加来源、口号、括号说明或延伸解释；图片生成方式与出处留在私有来源记录。按当前正文图片出现顺序重新编号，头图也纳入顺序，封面不额外编号。单篇作者主动删去头图图注或调整编号时保留当前终稿，不在归档时恢复；该例外不改变后续默认。
- 图数按本篇内容需要：001四张、002三张只是已用实例，不是下篇要求。

官方封面比例与正文/封面独立性的来源保留：[草稿接口文档](https://developers.weixin.qq.com/doc/service/api/draftbox/draftmanage/api_draft_add)。系列配色、纸艺及裁切取舍是本项目编辑选择，**不是官方强制**。

## 8. Python教学与原生代码验收

- 代码展示核心机制与控制流，不追求生产系统全功能。功能、字段和示例范围优先用精简块头/行内注释解释，避免在正文重复逐字段解说；代码前保留必要引入，代码后仅按理解需要补短说明。
- 接口名、异常路径、测试方式按当前topic设计；不继承 `rt`、`authorizer`、工具别名等旧代码接口，也不固定22/35或37/31行。
- 代码须保持合法Python、多行缩进；静态编译／AST能检验语法，mock／fixture验证适用的核心路径，不能称真实API测试或生产可运行。
- 工具调用展示结构化解析、必要校验与授权，不 `eval` 模型输出，不把外部内容当执行指令；不要为“短”省略决定安全与正确性的门禁。按机制检查输入类型、固定工具/来源权限、轮次与停止、候选验收、数据别名和回调异常；配置错误与运行失败分开，取消不得被普通异常吞掉。复制不是沙箱，轮次不替代时间/费用预算，格式合法不等于内容可信。适配器与验收回调未实现的能力写作假设，不冒称生产保障。
- 确定性测试逐项断言真实终态及工具未被执行等副作用，主动找反证。测试名不证明路径覆盖，例如只断言pause可能由后续回调耗尽产生；复制失败应用明确抛错夹具验证。通过AST、固定回调、真实模型及独立业务验收分别报告，不以测试数量代替覆盖。
- **公众号官方插入代码流程优先**。已验证平台结构包含 `section.code-snippet__js`、`pre.code-snippet__js`、实际语言标识（Python为`data-lang="python"`）、每行独立`code`、原生语法标记；类名是平台实测记录，随版本变化需现场核对，不冒充永久官方API。
- 灰底`pre`、`br`换行、两段计数、语言属性或一张首屏截图均不能独立证明正确。保存后重开，分别检查源码内容、行数、缩进、行号、多色语法高亮、长行横滚和真实读者呈现。
- 自动语言识别可能出错；现场确认实际语言。001单行docstring曾帮助识别，但不是通用识别保证，不为凑规则给每篇代码添加无意义docstring。

## 9. 事实与参考资料

- 原论文、协议与产品官方文档优先。术语、责任主体、产品行为、日期／版本和数量均可追溯；没有证据的性能、成本、排名、内部架构结论不写。
- 明确“官方定义／可观察产品行为／教学假设／实现建议／未知”，不让图片或伪代码把建议包装成事实。
- 每篇参考从[1]重新编号，不固定条数；文末用编号项目列表，推荐“[n] 来源方：标题（已核实日期或版本）｜完整原始URL”。不能猜日期，也不因好看删URL。
- 正文引用贴在具体受支持观点附近；在线协作稿可点到原始来源。公众号不接受普通外链时保留引用编号和文末完整纯文本URL，并说明载体差异，不声称可点击。
- **所有实际引用均可定位到具体源**。深链、版本说明等不要只留下不可点击“版本说明”四个字而无地址：将完整链接补入本篇来源映射／文末，或指向准确覆盖它的已有来源，不错绑编号。
- 图片图注、正文、表格和代码注释的编号与版本口径共同检查。迁移前的分篇参考索引保存在私有工作目录的 `wechat/legacy-references.md`。写稿时重新核对实际使用的来源。

## 10. 修改、同步与保存纪律

1. **核对目标**：具体账号、题目、文章状态和最新源。当前打开的另一篇后台页面不能代替用户指定文章。
2. **回读并备份**：在线稿与公众号都实时回读；保留原文、表格、图片位置／URL、代码、作者、摘要、封面和相关设置基线。多轮实时协作不可拿旧快照覆盖作者新改动。
3. **局部修改**：只改用户点名范围；标题/视觉改稿不顺手润色正文，不全篇回灌旧HTML破坏原生代码。已发表文章要求“保存草稿待发表”时复用为独立草稿，保留公开原文；已有新草稿则继续该稿，不重复创建。
4. **保存后重开**：检查标题/封面、非目标文字、图与表、Python内容和引用；直接style、图片属性或表格outerHTML可能不被富文本编辑器保存，采用现场可验证更新方式。
5. **官方读者预览**：新生成预览二维码→临时卡片→点击进入真实正文。检查每张图加载与语义、代码、多列布局和完整URL，不用云侧离线预览替代。
6. **窄屏检查并写清范围**：优先390px浏览器视口仿真；容器限宽仅叫“390px内容区检查”，842px浏览器只叫桌面检查，都不是微信手机真机。工具失败如实列未完成项，不套用历史结论。
7. **归档和交付**：归档最新保存正文与核验记录，更新私有公众号登记；平台HTML片段不当作完整离线预览。只交付最终文件／可访问入口，不混入旧“最终稿”和工作材料。

本项目“发布到草稿”一律解释为**保存草稿**；用户说“待我发表”就不点击发表、不群发、不向额外账号发送预览。线上发表、群发和定时发布由用户操作。向额外账号发送预览须有对应授权。

后续文章仅按项目本期流程生产：先更新微信公众号草稿，保存重开及官方读者预览后，由作者确认，再归档项目唯一正文与正式素材。私有 working 仅作候选、备份与核验，不是正式资源存档；不默认创建或同步另一份在线协作文档。用户明确指定协作文档时只在授权范围使用。保存后作者直接修改公众号内容，应以实时稿为准合并进候选，不恢复作者删文。网站准入、Git提交推送和部署仍须另行授权，不因草稿保存或项目存档自动执行。

已有原生代码选区粘贴若静默追加，立即回读，停止保存错误稿；只在已确认的有限code范围真实删除、核对空pre及语言仍在，再向空code粘贴纯源码。容器丢失才使用官方插入恢复，不回贴旧高亮HTML。逐行textContent只将NBSP映射为空格并允许尾换行，不能折叠任意空白掩盖缩进损坏。非代码块、全部table和媒体另行比较。图注插入不得沿用H1选区；标题继承或段落合并时仅恢复受影响有限范围，从最新备份恢复，不重放历史全文。

出现空嵌套表格时，只能在确认没有独立内容后清理空外层；不得删除有内容的表。保存后再预览也可能改变编辑器结构，预览之后再次检查。

已由作者自行发表时，直接回读其提供的正式URL和页面日期，以正式正文替代过期临时预览；保存重开观察仍用当时真实采集数据，独立投影并与发表全文比较，不能生成虚假新保存记录。发表前后仅包装或水印变化分别标明；若正文不同，重新审核公开终稿并取得其保存来源，不能把旧观察绑到新稿。先归档后用transition登记作者已完成的发表，不自动发表、不恢复已删除草稿，也不因发表而自动开放网站。

## 11. 豆包工作入口与稿件登记

1. 在豆包工作打开本仓库，用`node scripts/interview/issue.mjs next`按题单order选择新稿、title作为本期主题；已有稿件单列。确认本期范围后`start AE-ID`准备私有working，按[公众号模板](../templates/interview-wechat-article.md)写作，不提前改正式正文。旧稿续接保留历史标题与作者修改；最终项目Markdown只在保存回读核验后归档。
2. 使用面试规则定义的 `INTERVIEW_WORKSPACE`。打开其中的 `wechat/registry.json` 核对栏目和章内序号、协作源、已有草稿与公开原文。私有目录不可读或目标有歧义时，停在准备阶段，避免重复建稿。登记只保存可持久定位的信息和回读证据路径，不记录会话凭据或临时预览票据。
3. 对旧稿先用豆包工作回读在线协作稿、公众号账号及目标草稿，并记录版本和更新范围。同题存在公开文章、独立草稿或历史草稿时，逐一核对，按当前任务续接对应稿件。对新题先搜索账号内的同题草稿，再依照面试预览确认和草稿授权执行。
4. 优先使用已登录账号的官方编辑器更新现稿和原生代码块。使用 `baoyu-post-to-wechat` 前核对当前版本与能力。API `draft/add` 属于新建流程，不用于续稿。沿用明确授权的账号与通路。
5. 保存后重开并验读者页，实际采集记录按[本期格式](interview-content-contract.md#本期制作命令与资料格式)经record-saved核对；archive将最终同稿正文与正式媒体落仓，保留私有安全证据与登记。网站准入另须公开确认，不因归档自动上站，不提交推送。项目状态、网站可见性、公众号草稿与实际发表分别维护；公众号正式发表凭用户提供日期和真实链接登记。

### 私有资料边界

旧项目原件原地保全。凭据、登录态、二维码和历史临时票据不进入仓库。历史脚本只作追溯，归档 HTML 仅供比对。公众号保存要以本次实际回读和核验结果为准。
