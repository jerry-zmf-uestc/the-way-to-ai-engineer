# 章节写作规范

适用于 `book/` 正文。章节编号、实验和状态以[项目总体方案中的章节地图](../designs/project-plan.md#chapter-map)为准；Lab 入口遵循 [topic 规范](topic-contract.md)。

## 章节组织

章节需要覆盖真实问题、机制、可运行代码、失败边界、练习和来源，但正文主体不套固定的教学栏目。下面是可能的理解路径，不是逐项生成的标题模板：

```text
# 第 N 章：主题

开场：一个真实问题或一句心智模型（≤3 行），不写"前置知识/运行环境"套话行，
也不要在文前放"本章核心"摘要块——章节大纲（小节标题）就是核心内容的体现

## 主体若干节（标题按技术问题自然命名）
从实际困境进入，按读者理解顺序穿插机制、代码、运行结果与边界
复杂链路优先分层验证：先验证确定性底层，再加入模型、网络或并发
lab 的运行命令与关键输出嵌在对应位置，不另写项目管理式周任务栏目

在最能帮助判断的位置解释错误语义、排查路径、安全边界和练习
章末按主题需要收束并提供进一步阅读，不强制使用统一标题
```

页尾只保留返回目录、上一章、下一章的有效学习导航；没有正文的章节不显示链接，也不附加开发进度。运行环境、源码位置和示例类型等读者实际需要的信息仍写清楚。

普通章节不依赖 GoTrip 的实现状态。旅行场景可以作为独立示例题材；项目完整实现说明只在独立项目区维护。

## 写作风格

- **从具体问题开场**：不写“本周学什么”“为什么学”“修改哪里”“如何验收”等项目管理字段。用实际困境、失败现象或明确技术判断进入主题；复杂章节可以用一小段说明接下来要建立的链路。
- **不强制段落句式**：不要求每节都以加粗判断句开头，也不限制代码后的段落数量。定义、代码、图表和边界按理解需要组合，避免所有章节呈现同一种节拍。
- **判断句优先**：能写"Go 只有值传递"就不写"Go 在多数情况下采用值传递语义"。给出可执行的经验法则，代替面面俱到的场景罗列。
- **类比读者已有知识**：目标读者是 AI 工程师学员，多半会 Python 或 JS/TS；恰当时用对照（defer ≈ try/finally，go.mod ≈ package.json）降低迁移成本。
- **代码推动解释**：代码注释承载局部动作，正文解释设计、运行行为和代码说不出的边界。完整程序、源码摘录、示意片段和故意失败例必须用自然行文区分；不能让读者误以为缺少上下文的片段可以直接运行。
- **套话黑名单**：禁止"本章目标""本章小结""完成检查""示例中的分工""自检时，先选正常和边界输入预测结果""本章核心"等仪式性栏目与套话。章末可用"记住这几条"收束，最多 4 条。
- 表格只用于真实对比，不为形式存在。标题按主题自然命名；不要设置“问题与直觉”“概念与机制”“本周目标”“项目增量”“验收标准”或“GoTrip 本章增量”等固定栏目。
- 版本、依赖和兼容范围应解释选择理由。外部链路先提供不依赖模型密钥的最低层验证，再叠加真实 Provider；无法离线验证时明确边界。
- Session、并发、超时、权限、秘密和副作用应在相关实现附近讨论，不统一堆到章末制造“安全清单”。

## 技术深度

复杂章节不能只做到“概念 + 成功示例 + API 罗列”。应根据主题提供足以支持工程判断的证据：

- **版本与事实**：说明行为适用的版本或前提，能回到官方资料、源码或可重复实验；不仅列版本号，还解释为什么锁定。
- **语义分类**：把容易混为一谈的状态拆开，例如调用失败与结果不完整、事务回滚与提交结果未知、取消与超时、检索为空与检索被截断。
- **抽象边界**：指出相邻层各自包住什么、能访问哪些状态、责任在哪里结束；配置、提示词和客户端拦截不能冒充服务端授权。
- **分层验证**：先直接验证底层函数、协议或存储，再接入框架、Runtime 和模型。排错顺序必须能缩小故障层，而不是罗列互不相关的建议。
- **失败传播**：至少覆盖关键失败的触发条件、可观察现象、传播方式、恢复策略，以及调用方需要做出的选择。
- **安全闭环**：涉及副作用、文件、命令、租户、凭证或外部工具时，说明信任边界和最终强制执行点。

不是每章都需要错误矩阵或安全小节；但缺少这些内容时，审查记录必须能解释为什么该主题不需要。不能用固定标题存在、代码块数量或篇幅证明内容深入。

## 代码与命令

- 标明代码是完整程序、源码摘录、伪代码还是故意失败的示例。摘录链接到真实文件并说明放置位置。
- 来自 Lab 的函数必须与实际源码一致；教学变体明确标注，不伪称已有实现。
- 示例说明工作目录、所需版本、依赖、运行命令和输出。正文使用仓库相对路径。
- 不依赖某次观察到的随机顺序或扩容倍数；说明稳定条件和可变部分。
- 故意失败的代码使用临时目录或独立副本验证，不破坏正式 Lab。
- 改函数签名时，说明调用方和测试应怎样同步修改。
- 公共操作约定集中维护在 [示例与练习说明](../../book/introduction.md#running-examples)。

示例顺序：目的 → 文件位置 → 操作 → 命令 → 预期结果 → 说明（可压缩进代码注释，不单列栏目）。

错误案例顺序：错误表现 → 最小复现 → 原因 → 修复 → 再次验证。错误应在首次需要该判断的位置解释；章末排错表只用于检索，不能取代机制说明。

练习按内容选择紧凑表格或带注释的起点代码，每章只保留 1–2 道有代表性的任务；更细粒度的练习放进对应 Lab README 或测试。保留任务的边界条件，不用完整答案代替练习。第 1 章现有练习起点代码放在 tests/fixtures/chapter01-exercises.md，供样章校验提取。

多主题章（第 2、7 章）统一使用单文件，主题作为编号二级标题，练习按章连续编号（每主题 1 道）；主题和练习各设唯一锚点，避免链接落到其他主题的同名栏目。

## 阅读与维护

每页一个主标题，标题层级连续；必要解释保持展开。操作系统差异可用分段或 Tabs，连续操作可增强为 Stepper，标准 Markdown 仍应完整可读。只在关系难以用文字表达时增加图示，确实存在选择时才做对比表。

以旧书有效内容为基线，记录目标、概念、示例、错误、练习和资料的来源及去向。合并、删除、修正均写明原因，不能为缩短篇幅而跳过核心内容。篇幅和代码块数量只用于提示异常，不用于评分。

课程正文与维护记录分开：迁移源路径、commit/revision、meta.yml、内部审查链接以及"待恢复""等待确认"等状态，只在 docs 来源记录、章节地图和 spec 中维护，不写进正文。参考资料说明读者能从中学到什么，不使用"保留旧章入口"等编辑口吻。必要的出处署名和许可证声明仍须保留，不能借此省略归属要求。

## 验收

使用 [审查表](../templates/book-chapter-review.md) 核对学习目标覆盖、来源、代码一致性、实际操作结果和文字质量。实现、代码、内容审校、读者验证分别记录；自动测试不能证明读者已经学会。

每次变更运行 `make validate-docs`；代码或操作步骤变化时重跑受影响示例。试点额外运行 `ruby scripts/verify-book-pilots.rb`。未实施的章节不得标为已审校，没有读者反馈则保持读者验证待验证。

正文代码、操作步骤或文档检查器变化时，按 [AGENTS.md 测试要求](../../AGENTS.md#testing-requirements) 执行 `make validate-book`。具体脚本调用关系维护在 [Makefile](../../Makefile)，不在这里重复列清单。验证时注意以下边界：

- 结构检查覆盖当前 19 篇教学正文、44 道表格练习，以及前置说明、参考和导航；索引与导读不强套章节模板。栏目存在不代表讲解充分。这是迁移期的旧骨架检查；Phase 1 必须先补充语义审查与新页面反例，再放宽固定栏目假设。
- 第 2、7 章检查单文件结构、主题映射、连续题号和定位锚点；修改相关检查时须验证重复目录、缺锚点、错误题号和断链等反例。
- 全部章节已迁移到新骨架，结构检查只接受新骨架。
- 正文代码从书稿提取，在临时副本中检查编译、输出和声明的失败方式，不另存一份脱离正文的示例。当前专门验证第 3 章片段与第 1/2 章样章；不能因此声称全部练习答案、错误排查步骤都已验证。
- 文档验证拒绝公开页面依赖隐藏 spec、章节四维状态、AGENTS.md 的规则/模板引用和引言准备锚点。链接存在不证明实际遵守规范。
- 内容审校、代码验证与读者反馈分别记录；没有真人反馈时，读者验证仍为待验证。

写作依据：[GitBook 信息架构](https://gitbook.com/docs/guides/docs-best-practices/documentation-structure-tips)、[Diátaxis 教程](https://diataxis.fr/tutorials/)、[解释文档](https://diataxis.fr/explanation/)。本规范是项目自己的内容要求，并非外部框架逐项照搬。
