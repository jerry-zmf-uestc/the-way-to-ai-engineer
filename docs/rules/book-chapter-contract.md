# 章节写作规范

适用于 `content/book/` 正文。章节编号、实验和状态以[项目总体方案中的章节地图](../designs/project-plan.md#chapter-map)为准；Lab 入口遵循 [topic 规范](topic-contract.md)。

## 章节组织

章节正文以主题知识为主线：从现实问题进入，按职责、状态、协议、机制与设计取舍拆解核心知识点。代码与图示用来解释机制，正文不能写成配套Lab逐行导读或测试命令清单。练习、具体输出、测试名与操作导读放在Lab README和代码注释中，正文保留理解主题所需的例子。主体不套固定的教学栏目。下面是可能的理解路径，不是逐项生成的标题模板：

```text
# 第 N 章：主题

顶部：配套实验：[实验名称](Lab README)。

开场：一个真实问题或一句心智模型，不写"前置知识/运行环境"套话行，
也不要在文前放"本章核心"摘要块——章节大纲（小节标题）就是核心内容的体现

## 主体若干节（标题按技术问题自然命名）
从实际困境进入，按读者理解顺序穿插机制、代码、运行结果与边界
复杂链路优先分层验证：先验证确定性底层，再加入模型、网络或并发
按知识点安排代码、图示、过程示例与边界；Lab命令与测试导读留在实验中
复杂主题可按需要加入“最佳实践”和“常见问题排查”，不要求每章都有

在最能帮助判断的位置解释错误语义、排查路径、安全边界和练习
章末固定“小结”和“参考文档”；主体标题按主题适配
```

页尾只保留返回目录、上一章、下一章的有效学习导航；没有正文的章节不显示链接，也不附加开发进度。运行环境、源码位置和示例类型等读者实际需要的信息仍写清楚。

普通章节不依赖 GoTrip 的实现状态。旅行场景可以作为独立示例题材；项目完整实现说明只在独立项目区维护。

## 写作风格

- **从具体问题开场**：不写“本周学什么”“为什么学”“修改哪里”“如何验收”等项目管理字段。用实际困境、失败现象或明确技术判断进入主题；复杂章节可以用一小段说明接下来要建立的链路。
- **不强制段落句式**：不要求每节都以加粗判断句开头，也不限制代码后的段落数量。定义、代码、图表和边界按理解需要组合，避免所有章节呈现同一种节拍。
- **判断句优先**：能写"Go 只有值传递"就不写"Go 在多数情况下采用值传递语义"。给出可执行的经验法则，代替面面俱到的场景罗列。
- **类比读者已有知识**：目标读者以已有 TypeScript/React 经验、正在补 Go 后端与 Agent 工程能力的前端工程师为主，也覆盖其他已有软件工程经验的学习者。恰当时用对照（defer ≈ try/finally，go.mod ≈ package.json，Streaming ↔ SSE 页面状态，Session ↔ 服务端会话事实存储）降低迁移成本，但不要把类比写成主张本身。
- **补出迁移落点**：涉及 Runtime、Session、Context、RAG、Serving、Trace、Safety 等跨层主题时，至少在开头或首次关键转折处说明“这件事和前端已有经验如何对应、又在哪里失效”，帮助读者把页面交互、BFF/API、状态管理与服务端执行边界区分开。
- **代码解释机制**：正文选择必要的接口和关键片段，说明职责、信息流、决策条件和设计取舍；不要按main.go函数顺序组织整章。具体实验的计数、输出、测试断言和操作步骤由代码注释与Lab README承载。完整程序、源码摘录、示意片段和故意失败例必须用自然行文区分；不能让读者误以为缺少上下文的片段可以直接运行。
- **套话黑名单**：禁止"本章目标""本章小结""完成检查""示例中的分工""自检时，先选正常和边界输入预测结果""本章核心"等仪式性栏目与套话。章末使用“小结”收束，提炼3–5条工程判断。
- 表格只用于真实对比，不为形式存在。标题按主题自然命名；不要设置“问题与直觉”“概念与机制”“本周目标”“项目增量”“验收标准”或“GoTrip 本章增量”等固定栏目。
- 版本、依赖和兼容范围应解释选择理由。外部链路先提供不依赖模型密钥的最低层验证，再叠加真实 Provider；无法离线验证时明确边界。
- Session、并发、超时、权限、秘密和副作用应在相关实现附近讨论，不统一堆到章末制造“安全清单”。

## 架构讲解与证据边界

以最小决策闭环帮助读者定位新机制：它解决哪个具体问题，改变哪些输入、状态、动作或控制权，增加什么失败与代价，怎样证明效果和复杂度收益。这些是审查问题，不要求作为固定标题；具体构件边界见[总体方案的架构视角](../designs/project-plan.md#贯穿课程的架构视角从最小闭环理解扩展)。

- 区分任务目标、Provider生成停止原因、Runtime终态与业务验收；模型结束响应不等于任务完成。
- messages只是状态的一部分；Session、Context、长期Memory、RAG与Checkpoint按各自职责讲解，不把它们硬套成三层记忆。
- ReAct讲动作与观察反馈，调试以可核对的执行证据为基础；可见解释不等于完整内部推理。
- DAG、blockedBy、Lead、MessageBus、Cron、Hook数量和工具名属于具体实现选择，不写成Planning、多Agent或Workflow的通用定义。
- 分别检验机制、任务效果和新增复杂度的收益。fake通过只能证明对应契约，检索命中也不能替代答案证据校验；没有对照时说明结论范围。

## 技术深度

复杂章节不能只做到“概念 + 成功示例 + API 罗列”。应根据主题提供足以支持工程判断的证据：

- **版本与事实**：说明行为适用的版本或前提，能回到官方资料、源码或可重复实验；不仅列版本号，还解释为什么锁定。
- **语义分类**：把容易混为一谈的状态拆开，例如调用失败与结果不完整、事务回滚与提交结果未知、取消与超时、检索为空与检索被截断。
- **抽象边界**：指出相邻层各自包住什么、能访问哪些状态、责任在哪里结束；配置、提示词和客户端拦截不能冒充服务端授权。
- **分层验证**：先直接验证底层函数、协议或存储，再接入框架、Runtime 和模型。排错顺序必须能缩小故障层，而不是罗列互不相关的建议。
- **失败传播**：至少覆盖关键失败的触发条件、可观察现象、传播方式、恢复策略，以及调用方需要做出的选择。
- **安全闭环**：涉及副作用、文件、命令、租户、凭证或外部工具时，说明信任边界和最终强制执行点。

不是每章都需要错误矩阵或安全小节；但缺少这些内容时，审查记录必须能解释为什么该主题不需要。不能用固定标题存在、代码块数量或篇幅证明内容深入。

## 代码与命令

- 标明代码是完整程序、源码摘录、伪代码还是故意失败的示例。摘录链接到真实文件并说明放置位置。
- 来自 Lab 的函数必须与实际源码一致；教学变体明确标注，不伪称已有实现。
- 示例说明工作目录、所需版本、依赖、运行命令和输出。正文使用仓库相对路径。
- 不依赖某次观察到的随机顺序或扩容倍数；说明稳定条件和可变部分。
- 故意失败的代码使用临时目录或独立副本验证，不破坏正式 Lab。
- 改函数签名时，说明调用方和测试应怎样同步修改。
- 公共操作约定集中维护在 [示例与练习说明](../../content/book/introduction.md#running-examples)。

Lab操作说明顺序：目的 → 文件位置 → 操作 → 命令 → 预期结果 → 说明（可压缩进代码注释，不单列栏目）。正文围绕知识点解释代码，不因这个操作顺序而组织整章。

错误案例顺序：错误表现 → 最小复现 → 原因 → 修复 → 再次验证。错误应在首次需要该判断的位置解释；章末排错表只用于检索，不能取代机制说明。

练习按内容选择紧凑表格或带注释的起点代码，样章正文的练习放进顶部链接的Lab README，保留任务、边界和验证方式；其他正文暂时保留原练习栏目，待逐章迁移。保留任务的边界条件，不用完整答案代替练习。第 1 章现有练习起点代码放在 tests/fixtures/chapter01-exercises.md，供样章校验提取。

多主题章（第 2、7 章）统一使用单文件，主题作为编号二级标题，练习按章连续编号（每主题 1 道）；主题和练习各设唯一锚点，避免链接落到其他主题的同名栏目。

## 阅读与维护

每页一个主标题，标题层级连续；Part 3合章按任务链组织，保留相邻职责区别，避免将原章节逐篇拼接；主目录控制在清楚的阶段层级，细节通过小节和Lab承接；必要解释保持展开。操作系统差异可用分段或 Tabs，连续操作可增强为 Stepper，标准 Markdown 仍应完整可读。只在关系难以用文字表达时增加图示，确实存在选择时才做对比表。

以旧书有效内容为基线，记录目标、概念、示例、错误、练习和资料的来源及去向。合并、删除、修正均写明原因，不能为缩短篇幅而跳过核心内容。篇幅和代码块数量只用于提示异常，不用于评分。

课程正文与维护记录分开：迁移源路径、commit/revision、meta.yml、内部审查链接以及"待恢复""等待确认"等状态，只在 docs 来源记录、章节地图和 spec 中维护，不写进正文。参考资料说明读者能从中学到什么，不使用"保留旧章入口"等编辑口吻。必要的出处署名和许可证声明仍须保留，不能借此省略归属要求。

## 验收

使用 [审查表](../templates/book-chapter-review.md) 核对学习目标覆盖、来源、代码一致性、实际操作结果和文字质量。实现、代码、内容审校、读者验证分别记录；自动测试不能证明读者已经学会。

每次变更运行 `make validate-docs`；代码或操作步骤变化时重跑受影响示例。试点额外运行 `ruby scripts/verify-book-pilots.rb`。未实施的章节不得标为已审校，没有读者反馈则保持读者验证待验证。

正文代码、操作步骤或文档检查器变化时，按 [AGENTS.md 测试要求](../../AGENTS.md#testing-requirements) 执行 `make validate-book`。具体脚本调用关系维护在 [Makefile](../../Makefile)，不在这里重复列清单。验证时注意以下边界：

- 结构检查覆盖当前教学正文、练习表格、参考和导航；目录页不作为正文保留。Part 3按构建篇、运行时、治理篇整合后的16章正文使用顶部“配套实验”、文末“小结”和“参考文档”，练习在Lab README；其他现有正文暂时仍要求“踩坑清单、动手练、链接”三个定位标题。新增或迁移页面须同步检查器及反例，主体标题按技术问题自然组织。增加页面时同步完整性基线与缺页反例。栏目存在不代表讲解充分，不用数量代替语义审查。
- 第 2、7 章检查单文件结构、主题映射、连续题号和定位锚点；修改相关检查时须验证重复目录、缺锚点、错误题号和断链等反例。
- 结构检查明确区分已迁移基础正文与旧正文，不用旧固定栏目限制样章，不把规范更新等同于全部正文迁移完成。
- 当前Agent正文的真实源码摘录按manifest关联Lab和稳定共享包核对，允许省略整行注释与代码缩进，保留字符串与多行原文的差异；配套反例拒绝改值和改类型。这个校验不证明教学深度、算法正确或全量行为。新增教学变体/伪代码需明确性质并提供相应验证，不将变体伪称真实摘录。
- 当前Part 3图示的Python源/SVG配对在`public/diagrams/sources.json`登记。validate-book逐源在临时副本重建、比较产物并检查受限SVG结构与正文替代文字；缺源、额外/重复产物、过期SVG、活动/外部引用及缺替代文字反例不得通过。新增源格式先明确渲染契约。字节一致不证明图与实现语义或可读布局，仍需人工核对。
- 正文代码从书稿提取，在临时副本中检查编译、输出和声明的失败方式，不另存一份脱离正文的示例。当前专门验证第 3 章片段与第 1/2 章样章；不能因此声称全部练习答案、错误排查步骤都已验证。
- 文档验证拒绝公开页面依赖隐藏 spec、章节四维状态、AGENTS.md 的规则/模板引用和引言准备锚点。链接存在不证明实际遵守规范。
- 内容审校、代码验证与读者反馈分别记录；没有真人反馈时，读者验证仍为待验证。

写作依据：[GitBook 信息架构](https://gitbook.com/docs/guides/docs-best-practices/documentation-structure-tips)、[Diátaxis 教程](https://diataxis.fr/tutorials/)、[解释文档](https://diataxis.fr/explanation/)。本规范是项目自己的内容要求，并非外部框架逐项照搬。
